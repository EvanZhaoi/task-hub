# 23 - 第一期剩余功能实施计划

## 1. 本章目标

当前 TaskHub 已经完成任务发布、任务详情、单人投标和多人联合投标。本章重新安排第一期剩余工作，目标是尽快得到一个可以在测试环境完整演示的版本。

第一期最终必须支持两条路径：

```text
路径 A：招标
发布任务 -> 单人/多人投标 -> 发布者选标 -> 生成执行成员

路径 B：直接指派
发布任务 -> 指定负责人和协作者 -> 直接进入执行中
```

并提供以下快速查询入口：

```text
任务大厅 | 我发布的 | 我的投标 | 我参与的
```

## 2. 为什么这样排序

接下来的顺序是：

```text
1. 选标
2. 执行成员展示
3. 直接指定成员
4. 与我相关的任务
5. 权限和状态边界
6. 全链路测试与测试发布
```

原因：

- 选标是现有“发布 + 投标”链路缺失的最后一步，应最先完成。
- 执行成员由选标产生，必须紧跟选标验证复制结果。
- 直接指派复用同一套人员选择器和 TaskAssignee 展示，放在成员模型跑通后风险更低。
- “我参与的”依赖 TaskAssignee；直接指派完成后再做，数据语义才完整。
- 撤回、延期、主动流标等属于重要边界，但不应阻塞第一版核心路径测试。

## 3. 第一项：发布者选标

### 3.1 用户操作

1. 发布者进入自己发布的 OPEN 任务详情。
2. 查看每个 ACTIVE 投标的主投标人、协作者、金额、承诺交付日期、说明和附件。
3. 点击某条投标右侧的“选择该方案”。
4. 确认 Dialog 再次显示关键数据，避免误选。
5. 确认后任务变为“进行中”。

非发布者不显示选标按钮。前端隐藏只是体验优化，后端必须重新校验发布者工号。

### 3.2 页面设计

当前投标卡片已经突出三个关键字段：

```text
主投标人 | 投标金额 | 承诺交付日期
```

选标按钮放在 ACTIVE 投标卡片操作区，不能放在整张卡片上，避免误点击。

确认 Dialog 内容：

```text
确认选择此投标？

主投标人：张三（E10001）
协作成员：李四、王五
最终金额：¥3,500.00
最终交期：2026-11-30

[取消] [确认选标]
```

### 3.3 后端设计

新增 `SelectBidService`，由它控制完整事务：

```text
锁定 Task
    ↓
校验当前用户是发布者
    ↓
校验 Task.status = OPEN
    ↓
锁定并校验目标 Bid 属于该 Task 且为 ACTIVE
    ↓
目标 Bid -> ACCEPTED，active_key -> null
    ↓
其他 ACTIVE Bid -> LOST，active_key -> null
    ↓
读取目标 Bid 的唯一 OWNER
    ↓
Task -> ASSIGNED
    ↓
写 assigned_bid_id、primary_assignee_id、final_amount、final_delivery
    ↓
复制全部 BidMember 到 TaskAssignee
    ↓
Task.version + 1
    ↓
写 BID_ACCEPTED、TASK_ASSIGNED
    ↓
提交事务
```

### 3.4 测试重点

- 正常选标。
- 非任务发布者选标。
- Bid 不属于 URL 中的 Task。
- 目标 Bid 已撤回或已失败。
- Task 已被其他请求选标。
- 多人投标成员完整复制。
- 其他 ACTIVE Bid 全部变为 LOST。
- 任一步失败时事务整体回滚。

## 4. 第二项：执行成员展示

### 4.1 用户操作与显示

任务进入 ASSIGNED 后，详情页显示：

```text
任务成员

负责人  张三（E10001）
协作者  李四（E10002） 王五（E10003）
```

如果当前登录人属于执行成员，再显示轻量关系提示：

```text
你是该任务的负责人
```

或：

```text
你是该任务的协作成员
```

### 4.2 数据来源

只读取 `task_assignee`，不再从中标 Bid 实时推导。原因是 TaskAssignee 表达正式执行成员，后续交付权限也必须基于它判断。

人员接口可用时显示姓名和部门，不可用时退回显示工号，任务历史不能因为外部接口异常而无法查看。

## 5. 第三项：直接指定成员

### 5.1 用户操作

发布任务弹窗增加发布方式切换：

```text
[招标任务] [直接指派]
```

选择直接指派后：

- 隐藏招标截止时间。
- 必须选择一个负责人。
- 可以选择多个协作者。
- 保留标题、描述、金额、交付日期、复杂度、紧急标记、付款账号和附件。

### 5.2 页面设计

负责人使用单选人员选择器，协作者复用现有多人选择能力。负责人一旦选中，必须从协作者候选项中排除。

提交按钮根据模式显示：

```text
招标模式：发布任务
直接指派：发布并指派
```

### 5.3 后端设计

直接指派和招标发布的状态流转不同，使用独立 `CreateDirectTaskService`，不要让 `CreateTaskService` 充满条件分支。

事务：

```text
事务外：校验负责人和协作者都在人员目录中

事务内：
创建 Task，assignment_type = DIRECT，status = ASSIGNED
assigned_bid_id = null
primary_assignee_id = OWNER 工号
final_amount = budget
final_delivery = expected_delivery
写 TaskAssignee OWNER / COLLABORATOR
保存任务附件
写 TASK_CREATED
写 TASK_ASSIGNED
提交事务
```

第一期直接指派后不允许更换成员。

## 6. 第四项：与我相关的任务

### 6.1 交互方案

不新建三套列表页面。在任务大厅顶部增加第一层范围切换：

```text
任务大厅    我发布的    我的投标    我参与的
```

下一层继续保留当前状态 Tab：

```text
全部 / 招标中 / 待选标 / 进行中 / 已完成 / 已流标 / 已取消
```

这样可以组合查询：

```text
我发布的 + 待选标
我的投标 + 招标中
我参与的 + 进行中
```

范围切换使用 GET query string，例如：

```text
/tasks?scope=PUBLISHED
/tasks?scope=MY_BIDS
/tasks?scope=PARTICIPATED
```

这使页面可以刷新、收藏和分享当前查询地址，并继续使用 Laravel 分页。

### 6.2 “我发布的”

查询：

```text
task.created_by = CurrentUserService.employeeNo()
```

用途：发布者快速找到待选标、进行中或已完成任务。

卡片补充：

- “我发布的”关系标签。
- ACTIVE 投标数量。
- 待选标任务突出显示“去选标”入口。

### 6.3 “我的投标”

查询：

```text
task
WHERE EXISTS bid
WHERE EXISTS bid_member(
    user_id = 当前工号
    AND role = OWNER
)
```

卡片补充：

- 本人最新投标状态：有效 / 中标 / 未中标 / 已撤回。
- 本人报价。
- 投标版本。

“我的投标”只表达主投标人提交的方案，协作成员不放在此范围中。

### 6.4 “我参与的”

查询满足任意条件：

```text
1. 当前工号是某个 Bid 的 COLLABORATOR
2. 当前工号存在于 task_assignee
```

卡片关系标签根据实际数据显示：

- 协作投标。
- 任务负责人。
- 执行协作者。

任务查询必须去重。一个人可能先作为协作者投标，选标后又成为 TaskAssignee，页面只能显示一张任务卡片。

### 6.5 后端规则

- 当前工号只能从 `CurrentUserService` 获取。
- 不接受前端传入 `employeeNo` 查询其他人的“我的任务”。
- scope 必须使用允许枚举，非法值退回公开任务大厅。
- scope 与 keyword/status/complexity 一起应用到同一个 Task Query。
- 翻页必须保留全部 query string。

## 7. 第五项：权限与状态边界

核心业务规则以后端为准：

| 动作 | 后端必须校验 |
| --- | --- |
| 投标 | OPEN、未截止、非发布者、OWNER 无其他 ACTIVE Bid |
| 选标 | 当前人是发布者、Task OPEN、Bid 属于 Task 且 ACTIVE |
| 直接指派 | 人员真实存在、OWNER 唯一、成员不重复 |
| 查看全部投标 | 只有任务发布者；其他用户只看自己参与的 Bid |
| 我的任务范围 | 永远使用当前 Session 工号 |

TOP 是否可以代替发布者选标，本期不擅自开放。需要产品负责人明确后再增加。

### 8.2 业务验收场景

场景一：单人投标并选标。

```text
A 发布招标任务
B 单人投标
A 选择 B
Task = ASSIGNED
B = TaskAssignee OWNER
```

场景二：多人投标并选标。

```text
A 发布招标任务
B 带 C、D 联合投标
A 选择该方案
B = OWNER
C、D = COLLABORATOR
```

场景三：多个投标竞争。

```text
B、C 分别提交 ACTIVE Bid
A 选择 B
B 的 Bid = ACCEPTED
C 的 Bid = LOST
所有 active_key = null
```

场景四：直接指派。

```text
A 直接指派 B，并选择 C 为协作者
Task 直接进入 ASSIGNED
不生成 Bid
```

场景五：个人范围。

```text
A 在“我发布的”找到任务
B 在“我的投标”找到主投标记录
C 在“我参与的”找到协作任务
无关用户不能在个人范围看到该任务
```

### 8.3 发布前检查

- MySQL 8 实际数据库执行核心流程。
- 公司 SSO 登录和退出正常。
- 人员、付款账号、文件接口正常。
- 日志不输出 accessToken、clientSecret。
- 任务大厅和任务详情在常用桌面分辨率无溢出。
- 发布、投标、选标、直接指派失败时显示中文提示。
- 生产构建产物生成成功。
- 准备部署和回滚步骤。

## 9. 第一期候选项的处理

以下功能只有在上述必做项全部完成且测试稳定后才加入：

1. 撤回投标和重新投标。
2. 无投标自动流标。
3. 发布者主动流标。
4. 延长招标截止。
5. OPEN 状态取消任务。

不要为了加入这些边界功能，推迟选标、直接指派、个人任务入口和测试发布。
