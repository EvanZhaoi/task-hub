# 29 - 我的任务独立工作页

## 1. 本章目标

本章记录 TaskHub 如何把“我发布的”“我的投标”“执行任务”实现为三个独立工作页，并解决从任务详情返回时丢失筛选条件的问题。

本次不修改数据库，不改变发布、投标和选标事务，也不抽取现有发布任务弹窗。

## 2. 为什么不继续使用任务大厅 scope

三个入口的数据主体不同：

| 页面 | 查询主体 | 用户最关心的信息 |
| --- | --- | --- |
| 我发布的 | Task | 状态、投标数量、是否需要选标 |
| 我的投标 | Bid + BidMember | 报价、交期、投标状态、本人角色 |
| 执行任务 | TaskAssignee + Task | 最终金额、最终交期、执行角色和团队 |

如果全部放入 `Tasks/Index.tsx`，页面需要依赖 scope 参数切换查询、字段和卡片布局，文件会继续膨胀。独立页面让路由、查询和 UI 都围绕一个清晰职责展开。

顶部仍只占两个导航位置：

```text
任务大厅 | 我的任务⌄
               ├─ 我发布的
               ├─ 我的投标
               └─ 执行任务
```

“我的任务”是导航下拉菜单，不是 Tooltip，也不是承载页面内容的浮层。

## 3. 涉及文件

### 3.1 后端

- `routes/web.php`：注册三个受 SSO 保护的 GET 路由。
- `app/Http/Controllers/PublishedTaskController.php`：查询当前用户发布的 Task。
- `app/Http/Controllers/MyBidController.php`：查询当前用户作为 OWNER 或 COLLABORATOR 参与的 Bid。
- `app/Http/Controllers/AssignedTaskController.php`：查询当前用户的 TaskAssignee。
- `app/Services/TaskReturnNavigation.php`：校验详情页来源和返回地址。
- `TaskController.php`、`BidController.php`：下发并延续返回上下文。

### 3.2 前端

- `resources/js/Layouts/AppLayout.tsx`：增加“我的任务”下拉导航。
- `resources/js/Pages/MyTasks/Published.tsx`：发布任务管理视图。
- `resources/js/Pages/MyTasks/Bids.tsx`：投标记录视图。
- `resources/js/Pages/MyTasks/Assignments.tsx`：执行任务视图。
- `resources/js/components/my-tasks/MyTaskFilters.tsx`：三个页面共同使用的 GET 查询栏。
- `resources/js/components/my-tasks/PaginationNav.tsx`：分页导航。
- `resources/js/utils/task-navigation.ts`：生成携带来源页的详情地址。
- `resources/js/types/task.ts`：页面 Props 和列表项类型。

## 4. 路由与请求流程

三个页面都经过现有 `EnsureSsoAuthenticated` Middleware：

```php
// 当前用户发布的任务。
Route::get('/my-tasks/published', PublishedTaskController::class)
    ->name('my-tasks.published');

// 当前用户参与的投标历史，包括 OWNER 和 COLLABORATOR。
Route::get('/my-tasks/bids', MyBidController::class)
    ->name('my-tasks.bids');

// 当前用户已经成为正式执行成员的任务。
Route::get('/my-tasks/assignments', AssignedTaskController::class)
    ->name('my-tasks.assignments');
```

这里使用 invokable Controller，因为每个 Controller 只有一个页面动作。它类似 Spring MVC 中只提供一个查询方法的 Controller，但依然由 Laravel 容器注入 Request、CurrentUserService 和外部接口 Client。

## 5. 三个页面的查询规则

### 5.1 我发布的

```text
task.created_by = CurrentUserService.employeeNo()
```

- 关键词匹配标题或描述。
- 状态支持招标中、待选标、进行中、已完成、已流标和已取消。
- `PENDING_SELECTION` 仍是派生状态：Task 为 OPEN、截止时间已到、存在 ACTIVE Bid。
- 按 `created_at DESC` 排列。

### 5.2 我的投标

```text
Bid WHERE EXISTS BidMember(user_id = 当前工号)
```

- 不只查询 OWNER。联合投标的 COLLABORATOR 也属于真实投标参与者。
- 关键词匹配任务标题或投标说明。
- 状态筛选 ACTIVE、ACCEPTED、LOST、WITHDRAWN。
- 按 Bid 创建时间倒序，撤回重投历史不会被覆盖。

### 5.3 执行任务

```text
TaskAssignee.user_id = 当前工号
```

- 不把普通 BidMember 当成执行成员。
- 关键词匹配任务标题或描述。
- 状态筛选 ASSIGNED、COMPLETED、CANCELLED。
- ASSIGNED 优先；进行中任务按 `final_delivery ASC` 排列。

后端始终从 `CurrentUserService` 读取当前工号，不接受浏览器提交 employeeNo 查询其他用户。

## 6. 为什么页面筛选结构相同但状态不同

三个页面都使用：

```text
[关键词] [状态] [查询] [重置]
```

这能降低学习成本。但状态选项必须符合数据主体：

- “我发布的”筛选任务状态。
- “我的投标”筛选 Bid 状态。
- “执行任务”筛选正式执行阶段的 Task 状态。

因此 `MyTaskFilters` 只复用表单外壳，状态选项由页面传入，不在公共组件中硬编码业务规则。

## 7. 详情页返回原位置

### 7.1 前端生成 returnTo

用户进入详情时，`taskDetailUrl()` 把当前 pathname 和 query string 放入 `returnTo`：

```text
/my-tasks/published?keyword=接口&status=OPEN&page=2
    ↓
/tasks/10001?returnTo=%2Fmy-tasks%2Fpublished%3Fkeyword%3D...
```

这样关键词、状态和页码都能保留。

### 7.2 后端必须重新校验

浏览器参数不可信。`TaskReturnNavigation` 只允许：

```text
/tasks
/my-tasks/published
/my-tasks/bids
/my-tasks/assignments
```

允许附带 query string，但拒绝：

- `https://...` 外部绝对地址。
- `//example.com` 协议相对地址。
- 未知站内路径。
- 带 fragment 或控制字符的地址。

参数无效时退回 `/tasks`。这个限制避免 Open Redirect 安全问题。

### 7.3 投标和选标后继续保留

详情页的投标表单、选标表单都提交 `returnTo`。`BidController` 完成业务 Service 后，把合法参数重新附加到详情 URL，因此 Inertia 刷新完成后返回按钮仍指向原列表。

业务数据校验仍由 PlaceBidService 和 SelectBidService 完成；返回地址解析不进入业务事务。

## 8. UI 职责差异

### 8.1 我发布的

- 显示累计投标数和有效投标数。
- 待选标任务使用明显但克制的“去选标”按钮。
- 显示发布时间、截止时间和预算/确定金额。

### 8.2 我的投标

- 以一条 Bid 为一条记录。
- 突出报价、承诺交期和 ACTIVE/ACCEPTED/LOST/WITHDRAWN。
- 显示当前用户是主投标人还是协作成员。

### 8.3 执行任务

- 突出最终金额和最终交期。
- 显示负责人/协作成员身份和正式执行团队。
- 使用双列工作卡片，方便扫描当前进行中的工作。

## 9. 与 Spring Boot 的概念对照

| Laravel | Spring Boot 近似概念 | 说明 |
| --- | --- | --- |
| `Route::get()` | `@GetMapping` | Laravel 可以在集中路由文件中绑定 Controller |
| Invokable Controller | 只有一个 handler 的 Controller | `__invoke()` 由路由直接调用 |
| `CurrentUserService` | 当前认证用户 Service | TaskHub 不使用本地 users 表 |
| Eloquent `whereHas` | JPA relationship 子查询 / Specification | 用关联存在性筛选 BidMember、TaskAssignee |
| Inertia Props | MVC Model / ViewModel | 数据被序列化给 React 页面，不返回 REST JSON 页面 |
| `withQueryString()` | 分页链接保留查询参数 | Laravel Paginator 自动生成前后页 URL |

## 11. 常见错误

### 11.1 协作成员看不到“我的投标”

检查查询是否错误地限定 `bid_member.role = OWNER`。当前规则是 OWNER 和 COLLABORATOR 都可见。

### 11.2 投标后返回按钮变成任务大厅

检查投标表单是否提交 `returnTo`，以及 `BidController` 是否通过 `TaskReturnNavigation::safeUrl()` 后继续附加参数。

### 11.3 详情返回后筛选丢失

列表进入详情必须使用 `taskDetailUrl()`，不要手写 `/tasks/{id}`。分页查询还必须保留 `withQueryString()`。

### 11.4 DropdownMenu 类型或构建失败

确认安装的是 `@radix-ui/react-dropdown-menu`，并运行 `npm install` 更新依赖。

## 12. 本章完成效果

- 顶部导航保持紧凑。
- 三类个人工作有独立 URL、查询和 UI。
- 联合投标协作者不会从“我的投标”遗漏。
- 正式执行任务只以 TaskAssignee 为准。
- 详情返回、投标和选标之后仍保留原页面上下文。
- 没有修改数据库，也没有把现有发布任务弹窗拆成新组件。
