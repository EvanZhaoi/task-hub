# 36 - 第一期发布者手动完成任务

## 1. 本章目标

第一期尚未开发正式交付与验收流程。为了避免任务选标或直接指派后永远停留在“进行中”，本章增加一个临时但完整的任务完结能力：任务发布者可以将 `ASSIGNED` 任务手动确认完成。

该功能遵守以下边界：

- 只有任务发布者可以操作。
- 只有 `ASSIGNED` 任务可以完成。
- 操作不可撤销，前端必须二次确认。
- 使用 Task `version` 防止旧页面覆盖新数据。
- 状态、完成时间、版本和事件必须在同一个数据库事务内更新。
- 事务成功后邮件通知任务负责人和协作成员。
- 第二期接入 TaskDelivery 后关闭该手动入口，改由交付验收驱动完成。

## 2. 学习目标

完成本章后，应能理解：

1. 为什么 Controller 只处理 HTTP，上下文和跳转，完整业务流程放进动作 Service。
2. 为什么前端隐藏按钮不能代替后端权限校验。
3. 悲观锁 `lockForUpdate()` 与乐观锁 `version` 如何共同保护状态变更。
4. 为什么邮件要在事务提交后发送，且邮件失败不能回滚已完成的任务。
5. 如何通过 TaskEvent 区分第一期手动完成与第二期交付验收完成。

## 3. 最终效果

发布者打开进行中的任务详情，可以看到“确认完成”按钮：

```text
进行中的任务详情
    ↓
点击“确认完成”
    ↓
确认 Dialog 提示操作不可撤销
    ↓
POST /tasks/{task}/complete，携带当前 version
    ↓
CompleteTaskService 锁定并校验任务
    ↓
Task.status = COMPLETED
Task.completed_at = 当前时间
Task.version = version + 1
写入 TASK_COMPLETED
    ↓
提交事务
    ↓
邮件通知全部执行成员
```

非发布者、非 `ASSIGNED` 状态或使用旧版本提交时，后端返回中文校验错误，不修改任何业务数据。

## 5. 实现步骤

### 5.1 使用 Artisan 生成骨架

在项目根目录执行：

```bash
# FormRequest 只负责 HTTP 输入校验。
php artisan make:request CompleteTaskRequest

# 单动作 Controller 使用 __invoke，路由职责更明确。
php artisan make:controller TaskCompletionController --invokable

# Laravel 没有强制 Service 命令，因此使用 make:class 生成普通业务类。
php artisan make:class Services/CompleteTaskService

# 生成邮件类及普通 Blade 模板。
# Mailable 最终使用 Content(text: ...)，只发送简单纯文本和任务链接。
php artisan make:mail TaskCompletedMail --view=mail.tasks.task-completed
```

这些命令只生成文件骨架，业务规则仍需要按后续步骤填写。

### 5.2 校验请求

`CompleteTaskRequest` 接收两个字段：

```php
public function rules(): array
{
    return [
        // 页面打开时取得的 Task version，用于发现并发修改。
        'version' => ['required', 'integer', 'min:0'],

        // 详情页返回来源，只允许交给后端白名单服务继续处理。
        'returnTo' => ['nullable', 'string', 'max:2000'],
    ];
}
```

`authorize()` 返回 `true` 不代表任何人都能完成任务。FormRequest 只做输入格式检查，真正依赖数据库状态的权限规则必须在事务锁定 Task 后判断。

### 5.3 注册路由和 Controller

路由使用 POST，因为该动作会改变服务端状态：

```php
Route::post('/tasks/{task}/complete', TaskCompletionController::class)
    ->name('tasks.complete');
```

Controller 的执行顺序保持简洁：

```text
读取已校验参数
    ↓
从 CurrentUserService 取得当前 SSO 用户和动态 access token
    ↓
调用 CompleteTaskService
    ↓
按安全 returnTo 返回任务详情并显示成功提示
```

它不直接开启事务，也不在 Controller 中拼装 TaskEvent 或发送邮件。

### 5.4 完成任务事务

`CompleteTaskService::execute()` 是完整业务动作。事务内按以下顺序执行：

1. 根据主键重新查询 Task，并调用 `lockForUpdate()`。
2. 校验当前工号等于 `created_by`。
3. 校验 Task 状态为 `ASSIGNED`。
4. 校验数据库 `version` 等于请求携带的 `baseVersion`。
5. 校验任务至少存在一名 TaskAssignee。
6. 更新状态、完成时间、更新人和版本。
7. 追加 `TASK_COMPLETED` 事件。
8. 提交事务。

事件数据保留完成方式：

```php
'event_data' => [
    // 第二期可改用 DELIVERY_ACCEPTED，并在事件中记录 deliveryId。
    'completionMode' => 'MANUAL_PHASE_ONE',
    'completedAt' => $completedAt->toISOString(),
],
```

`lockForUpdate()` 防止两个请求同时修改同一任务；`version` 则能识别用户在旧页面上提交的操作。两者解决的问题不同，因此同时保留。

### 5.5 事务提交后发送通知

任务完成后读取全部 TaskAssignee，再通过已有人员大列表取得邮箱。每位成员单独收件：

- OWNER 邮件中显示“负责人”。
- COLLABORATOR 邮件中显示“协作成员”。
- 没有邮箱的成员写诊断日志，但不影响其他成员。
- 人员接口或 SMTP 失败只记录日志，不回滚已经提交的任务。

这里沿用用户 Session 中的动态 access token，不把 token 写入配置、前端或日志。

### 5.6 前端二次确认

详情页只在后端返回 `canComplete = true` 时展示 `CompleteTaskDialog`。Dialog 提交：

```ts
form.post(`/tasks/${taskId}/complete`, {
    // 保持详情页滚动位置，失败时用户仍能看到原上下文。
    preserveScroll: true,
});
```

表单数据包含当前 Task `version`。`canComplete` 只是页面入口控制，不能替代后端事务中的权限和状态校验。

## 6. 与 Spring Boot 的概念对照

| Laravel | Spring Boot 近似概念 | 差异 |
|---|---|---|
| FormRequest | `@Valid` DTO + 自定义校验消息 | Laravel 同时封装 authorize、rules 和 errors |
| Invokable Controller | 只有一个 Handler 方法的 Controller | Laravel 通过 `__invoke()` 直接作为路由动作 |
| Service | `@Service` | Laravel Service 默认不需要注解，容器按构造函数自动注入 |
| `DB::transaction()` | `@Transactional` | Laravel 常用闭包显式表示事务边界 |
| `lockForUpdate()` | JPA `PESSIMISTIC_WRITE` | 都要求处于事务内 |
| Task `version` | JPA `@Version` | 当前项目由业务 Service 显式比较并递增 |
| Mailable | JavaMail/Mail Service 的邮件对象 | Laravel 将主题、模板和数据封装在 Mailable 中 |
| Inertia `useForm` | MVC 表单 + 前端请求状态 | 页面仍由 Laravel 路由驱动，不是独立 REST SPA |

## 8. 常见错误

### 页面没有“确认完成”按钮

检查当前用户是否为 `created_by`，以及 Task 是否仍为 `ASSIGNED`。直接修改前端 Props 不能绕过后端校验。

### 提示“任务数据已经发生变化”

表示页面中的 `version` 已过期。刷新详情页获取最新任务数据后，再判断是否仍需要完成。

### 状态已完成但没有收到邮件

完成事务与邮件通知故意解耦。检查 Laravel 日志中的人员邮箱缺失、人员接口失败或 SMTP 失败记录；不要通过回滚任务状态来补偿邮件失败。

### 完成后重复点击

第二次请求会在事务内读到 `COMPLETED`，并返回“只有进行中的任务可以确认完成”，不会重复写事件或重复发送邮件。
