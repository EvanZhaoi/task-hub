# 38 - 第一期权限与状态边界检查

## 1. 本章目标

第一期核心功能已经能够完成发布、投标、撤回、选标、直接指派和手动完成。本章不新增业务功能，而是检查用户能否通过手工构造 URL 或请求参数绕过页面限制。

需要确认两件事：

1. 前端隐藏按钮只改善操作体验，真正的数据权限始终由 Laravel 后端判断。
2. 涉及状态变化的判断必须在数据库事务锁定最新记录后执行，不能信任页面打开时取得的旧状态。

## 2. 学习目标

完成本章后，应理解：

- 为什么 `FormRequest::authorize()` 返回 `true` 不等于放弃权限控制。
- 为什么 TaskHub 把依赖最新数据库状态的权限判断放在业务 Service 中。
- 为什么路由同时出现 `{task}` 和 `{bid}` 时仍要检查两者的业务归属。
- 如何用 Feature Test 证明非法请求既失败，又没有产生部分数据。

## 3. 最终效果

本次检查确认以下边界由后端强制执行：

| 业务动作 | 后端边界 |
| --- | --- |
| 投标 | Task 必须为 `OPEN`、未截止、操作者不是发布者、同一 OWNER 没有其他 `ACTIVE` Bid |
| 撤回 | Task 必须为 `OPEN` 且未截止；Bid 必须属于该 Task、状态为 `ACTIVE`；操作者必须是 OWNER |
| 选标 | 操作者必须是发布者；Task 必须为 `BIDDING + OPEN`；Bid 必须属于该 Task 且为 `ACTIVE` |
| 直接指派 | OWNER 和协作者必须来自真实人员目录；OWNER 唯一且不能同时作为协作者 |
| 手动完成 | 操作者必须是发布者；Task 必须为 `ASSIGNED`；version 一致；至少存在一名正式执行成员 |

## 6. 实现检查

### 6.1 HTTP 层只负责请求入口

以撤回投标为例，`BidController` 不根据前端按钮或路由参数直接更新数据库，而是把当前用户、Task 和 Bid 交给 `WithdrawBidService`。

```php
// Controller 只组织 HTTP 上下文，不在这里拼接撤回事务。
$withdrawBid->execute(
    task: $task,
    bid: $bid,
    user: $currentUser->user(),
);
```

`FormRequest` 负责字段形态。OWNER 身份、Task 状态和截止时间都可能在请求到达前发生变化，所以必须由 Service 在事务中读取最新数据后判断。

### 6.2 状态判断放在锁内

```php
// 锁定最新 Task，避免投标与选标、流标同时发生时使用旧状态。
$lockedTask = Task::query()
    ->whereKey($task->id)
    ->lockForUpdate()
    ->firstOrFail();

// 所有真正影响数据合法性的规则都针对锁定后的记录执行。
$this->assertTaskCanReceiveBid($lockedTask, $employeeNo);
```

这与 Spring 中在 `@Transactional` 方法内使用悲观锁读取实体后再校验的思路相同。区别是 Laravel 常用 `DB::transaction()` 闭包显式表达事务范围。

### 6.3 防止跨对象访问

Laravel 的路由模型绑定能根据 ID 找到 Task 和 Bid，但默认不会证明这个 Bid 属于 URL 中的 Task。因此撤回和选标都必须检查：

```php
// 防止把其他任务的 Bid ID 拼接到当前任务 URL 中。
if ((string) $bid->task_id !== (string) $task->id) {
    throw ValidationException::withMessages([
        'bid' => '目标投标不属于当前任务。',
    ]);
}
```

这种风险通常称为 IDOR，即用户通过替换资源 ID 访问或修改不属于当前上下文的数据。

### 6.4 非法请求必须没有副作用

本章测试不只检查中文错误，还检查数据库保持不变：

```php
// 跨任务撤回失败后，原投标仍然有效，也不能产生撤回事件。
expect(DB::table('bid')->where('id', 21023)->value('status'))->toBe('ACTIVE')
    ->and(DB::table('task_event')->where('event_type', 'BID_WITHDRAWN')->exists())->toBeFalse();
```

这比只断言 HTTP 重定向更可靠。即使未来有人调整异常处理，测试仍能阻止“页面提示失败但数据库已经修改”的回归。

## 7. 本次新增测试

### 7.1 投标入口边界

同一测试覆盖三种常见绕过方式：

1. 发布者手工请求自己的投标接口。
2. Task 仍为 `OPEN`，但 `bidding_deadline` 已经过期。
3. OWNER 已有一条 `ACTIVE` Bid，仍尝试重复提交。

三种请求都必须返回中文字段错误，并且不能新增 Bid 或 `BID_SUBMITTED` 事件。

### 7.2 跨任务撤回

测试把属于任务 A 的 Bid ID 放进任务 B 的撤回 URL。即使当前用户确实是该 Bid 的 OWNER，也必须因为 Task/Bid 不匹配而拒绝。

### 7.3 已有覆盖

现有 Feature Test 已继续覆盖：

- COLLABORATOR 不能撤回 OWNER 的投标。
- 截止后不能撤回。
- 非发布者不能选标。
- 发布者不能选择其他任务的 Bid。
- 已选标任务不能重复选标。
- 直接指派拒绝目录外成员和 OWNER/协作者重复。
- 非发布者不能手动完成任务。
- 旧 version 不能覆盖最新 Task。

## 8. Laravel 与 Spring Boot 对照

| Laravel | Spring Boot | 说明 |
| --- | --- | --- |
| Middleware | Filter / Interceptor | 处理 SSO 登录这一类请求级前置条件 |
| FormRequest | Bean Validation + 请求 DTO | 校验输入格式，不替代依赖数据库状态的业务权限 |
| Service `execute()` | `@Service` 业务方法 | 表达一个完整业务动作 |
| `DB::transaction()` | `@Transactional` | 保证多表修改原子性 |
| `lockForUpdate()` | `PESSIMISTIC_WRITE` | 锁定最新记录后再判断状态 |
| `ValidationException` | 业务异常 + 字段错误响应 | 向 Inertia 表单返回中文业务错误 |
| Pest Feature Test | MockMvc / 集成测试 | 从路由入口验证权限、事务和数据库副作用 |

## 9. 如何验证

自动测试之外，测试环境至少使用三个不同工号完成以下人工检查：

1. 发布者打开自己的任务，看不到投标入口；手工请求接口仍被拒绝。
2. 普通用户可以在截止前投标，但不能重复提交有效投标。
3. COLLABORATOR 能查看共同投标，但不能撤回或代表 OWNER 操作。
4. 只有发布者可以选择中标方案和确认任务完成。
5. 选标后重复提交原选标请求，不新增 TaskAssignee 和 TaskEvent。

## 10. 常见错误

### 10.1 只在 React 中隐藏按钮

浏览器代码由用户控制。用户仍可通过开发者工具或 API 工具构造 POST 请求，因此后端必须重复校验。

### 10.2 在 Controller 锁外读取状态

读取到 `OPEN` 后，另一个请求可能立即完成选标。应由业务 Service 开启事务、锁定 Task，再检查最新状态。

### 10.3 认为路由模型绑定会自动校验父子关系

`Task $task` 和 `Bid $bid` 分别绑定成功，不代表两者相关。除非使用并正确配置 scoped binding，否则仍要显式检查 `bid.task_id`。

### 10.4 只断言请求失败

边界测试还应断言 Task、Bid、TaskAssignee 和 TaskEvent 没有被部分修改。
