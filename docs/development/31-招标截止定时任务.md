# 31 - 招标截止定时任务

## 1. 本章目标

本章记录 TaskHub 如何自动处理已到招标截止时间的任务。定时任务只处理 `assignment_type = BIDDING` 且 `status = OPEN` 的数据，不会改动已选标的 `ASSIGNED` 任务。

完成后具备两个业务分支：

1. 截止时没有 ACTIVE 投标：任务自动变为 `FAILED`，写入流标事件并邮件通知发布者。
2. 截止时存在 ACTIVE 投标：任务保持 `OPEN`，页面派生显示“待选标”，写入截止事件并邮件提醒发布者。

## 2. 业务规则

```text
BIDDING + OPEN + bidding_deadline <= now()
    │
    ├─ 不存在 ACTIVE Bid
    │    → Task.status = FAILED
    │    → Task.version + 1
    │    → TASK_FAILED / NO_BID_TIMEOUT
    │    → 邮件通知发布者已流标
    │
    └─ 存在 ACTIVE Bid
         → Task.status 仍为 OPEN
         → BIDDING_DEADLINE_REACHED
         → 邮件提醒发布者选标
```

“待选标”只是页面根据状态、截止时间和有效投标数量计算出的显示状态，不是新的 TaskStatus。

## 3. 涉及文件

| 文件 | 作用 |
| --- | --- |

| `app/Services/ExpireOpenTasksService.php` | 在独立事务中处理一个任务 |
| `app/Services/TaskEmailNotificationService.php` | 事务提交后发送截止邮件 |
| `app/Mail/BiddingSelectionRequiredMail.php` | 待选标邮件对象 |
| `app/Mail/TaskFailedNoBidMail.php` | 自动流标邮件对象 |

| `database/patches/20261110_add_bidding_deadline_event.sql` | 已有 MySQL 数据库的一次性升级脚本 |

## 4. 为什么使用“一个 Scheduler + 分批扫描”

项目不为每个任务创建一条 Cron。任务数增长后，逐任务 Cron 会导致调度配置数量难以管理。Laravel Scheduler 每分钟启动一次命令，由数据库索引查找到期数据，更符合当前单体项目。

命令的稳定性措施：

- 每批最多 100 条，但不是每轮只处理 100 条。
- 处理完一批后使用 `bidding_deadline + id` 游标继续查询下一批。
- 单轮最多运行 45 秒，未处理数据由下一分钟继续。
- 不使用 OFFSET，避免任务在处理后离开 `OPEN` 集合造成跳行。
- `withoutOverlapping(10)` 防止上一轮未结束时再启动一轮。
- 单个任务失败只记日志，不中断后续任务。

## 5. 为什么每个任务使用独立短事务

命令先查到候选 ID，`ExpireOpenTasksService` 再锁定单个 Task 并重新校验。这可以处理“扫描刚完成，发布者立即选标”的并发情况：定时任务获得行锁后会读到 `ASSIGNED`，然后直接跳过。

如果把整批任务放在一个大事务中，一条数据异常可能回滚整批，并且会长时间占用大量行锁。当前方案将影响限制在单个任务内。

## 6. 幂等与邮件

定时命令会重复扫描仍为 `OPEN` 的待选标任务。为避免每分钟重复发邮件，系统使用“任务 ID + 当前截止时间”判断 `BIDDING_DEADLINE_REACHED` 是否已记录。

- 同一截止时间只写一次事件、发一次邮件。
- 发布者延长截止时间后，新截止时间可以再次触发提醒。
- 邮件在事务提交后发送，SMTP 失败只记日志，不回滚任务状态。
- 后台 Scheduler 没有浏览器 Session 和动态 SSO token，因此使用 `created_by_snapshot.email` 作为收件人。
- 历史快照缺少邮箱时只记录警告，不伪造固定 token，也不影响截止状态处理。

## 7. 数据库升级

新建数据库直接执行 `database/schema.sql`。已经存在的 TaskHub 数据库只执行一次：

```bash
# 在项目根目录执行；请将连接信息替换为当前环境实际值。
mysql -h 127.0.0.1 -P 3306 -u taskhub -p taskhub \
  < database/patches/20261110_add_bidding_deadline_event.sql
```

升级脚本只做两件事：

1. 将扫描索引调整为 `task(status, bidding_deadline)`。
2. 允许 `task_event.event_type = BIDDING_DEADLINE_REACHED`。

## 8. 调度启动方式

本地学习可以直接启动 Scheduler：

```bash
# 持续运行，仅用于本地开发。
php artisan schedule:work
```

也可以手动执行一轮，方便验证：

```bash
# 只扫描和处理一轮候选任务。
php artisan taskhub:expire-open-tasks
```

生产环境只需配置一条系统 Cron，每分钟调用 Laravel Scheduler：

```cron
* * * * * cd /path/to/task-hub && php artisan schedule:run >> /dev/null 2>&1
```

`/path/to/task-hub` 是部署机器上的项目根目录，需要替换成实际路径。这是唯一需要的 Cron，业务调度频率继续由 `routes/console.php` 管理。

## 9. 验证方法

```bash
# 确认命令已注册。
php artisan list | grep taskhub:expire-open-tasks

# 确认每分钟调度已注册。
php artisan schedule:list

# 运行截止功能专项测试。
php artisan test tests/Feature/ExpireOpenTasksCommandTest.php
```

专项测试覆盖：

- 无有效投标时自动流标并发邮件。
- 有效投标时保持 `OPEN`，事件和提醒只生成一次。
- `ASSIGNED` 任务完全跳过。
- 105 条任务能跨越首批 100 条继续处理。

## 10. 常见问题

### 命令手动执行成功，但没有每分钟自动执行

检查生产机器是否配置了 `php artisan schedule:run`。`routes/console.php` 只定义调度规则，不会自己唤醒 PHP 进程。

### 数据库拒绝写入 `BIDDING_DEADLINE_REACHED`

说明现有 MySQL 仍使用旧的 CHECK 约束。执行 `database/patches/20261110_add_bidding_deadline_event.sql`，再重试命令。

### 任务状态已正确变化，但没有收到邮件

先检查 Laravel 日志中是否有“发布者快照没有可用邮箱”或 SMTP 错误。后台命令不使用固定个人 Token 查人员信息，历史任务快照无邮箱时会跳过邮件，但不影响业务处理。

## 11. 本章完成效果

TaskHub 已能稳定区分“无投标自动流标”和“有投标等待选标”，同时对已选标任务保持无操作。下一项第一期功能是发布者主动流标。
