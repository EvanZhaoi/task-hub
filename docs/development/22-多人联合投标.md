# 22 - 多人联合投标

## 1. 本章目标

在现有单人投标基础上增加联合投标能力：当前登录人固定为主投标人（`OWNER`），可以从本据点人员列表中选择多名协作成员（`COLLABORATOR`）。

本章完成的是一个完整业务闭环：

```text
打开任务详情
    ↓
Laravel 从人员缓存加载候选人
    ↓
React 搜索并选择协作成员
    ↓
提交 amount / deliveryDate / collaboratorEmployeeNos / attachments
    ↓
FormRequest 校验请求结构
    ↓
PlaceBidService 在事务外校验人员真实性
    ↓
数据库事务写入 bid、bid_member、attachment_ref、task_event
    ↓
任务详情展示主投标人和协作成员
```

## 2. 学习目标

完成本章后，应理解：

- 为什么前端选择器返回的工号仍需要后端校验。
- 为什么外部人员接口不能放在数据库事务中调用。
- Laravel `FormRequest` 与业务 `Service` 分别校验什么。
- 为什么主投标人和协作者统一保存在 `bid_member`。
- Inertia Props 如何把人员目录从 PHP 传给 React。
- 如何在不引入全局状态管理的情况下实现多人选择器。

## 3. 前置条件

在项目根目录确认依赖和基础测试可用：

```bash
# 命令执行目录：TaskHub 项目根目录。
php artisan about
npm run typecheck
php artisan test
```

数据库必须已经存在以下表：

- `task`
- `bid`
- `bid_member`
- `attachment_ref`
- `task_event`

本功能不修改 `database/schema.sql`。当前结构已经支持一个 OWNER 和多个 COLLABORATOR。

## 4. 最终效果

用户打开仍在招标中的任务详情后：

1. 点击“我要投标”。
2. 填写金额和承诺交付日期。
3. 在“协作成员”中按姓名、工号或部门搜索人员。
4. 可以连续选择多名成员，也可以删除已选成员。
5. 不选择协作者时仍按原有单人投标流程提交。
6. 提交成功后，投标记录显示主投标人和全部协作成员。

## 6. 第一步：扩展投标请求结构

### 6.1 前端提交格式

多人投标新增一个字段：

```json
{
    "amount": "4500.00",
    "deliveryDate": "2026-11-20",
    "proposal": "三人协作完成开发和测试。",
    "collaboratorEmployeeNos": ["E30001", "E30002"],
    "attachments": []
}
```

注意：请求中没有 `ownerEmployeeNo`。OWNER 必须由后端读取当前登录用户，不能允许浏览器指定，否则用户可以冒用其他人工号投标。

### 6.2 FormRequest 校验

`StoreBidRequest::rules()` 增加：

```php
// 协作成员允许为空，空数组表示单人投标。
'collaboratorEmployeeNos' => ['nullable', 'array', 'max:20'],

// 工号最大长度与数据库 VARCHAR(32) 一致；distinct 阻止同一成员重复提交。
'collaboratorEmployeeNos.*' => ['required', 'string', 'max:32', 'distinct'],
```

这里校验的是 HTTP 数据结构，不负责判断工号是否真实存在。工号真实性依赖外部人员目录，属于业务校验，应放到 `PlaceBidService`。

## 7. 第二步：把动态 Token 交给业务 Service

`BidController::store()` 使用 `CurrentUserService` 读取当前 Session 中的动态 accessToken：

```php
$placeBid->execute(
    task: $task,
    validated: $request->validated(),
    attachments: $request->attachments(),
    user: $currentUser->user(),
    // 这是本次 SSO 登录得到的动态 Token，不是 .env 中的固定值。
    accessToken: $currentUser->accessToken(),
);
```

Controller 仍然只负责 HTTP 输入输出。它不直接调用人员接口，也不自己写数据库事务。

## 8. 第三步：后端校验协作成员

`PlaceBidService` 注入 `PersonnelClient`：

```php
public function __construct(
    private readonly SnowflakeId $ids,
    // 外部人员访问统一由 Integration Client 负责。
    private readonly PersonnelClient $personnel,
) {}
```

执行顺序是：

```php
// 外部接口调用在事务外完成，避免网络等待期间长时间占用 task 行锁。
$collaboratorEmployeeNos = $this->resolveCollaboratorEmployeeNos(
    $validated['collaboratorEmployeeNos'] ?? [],
    $user->employeeNo(),
    $accessToken,
);

return DB::transaction(function () {
    // 这里只执行必须原子完成的数据库写入。
});
```

`resolveCollaboratorEmployeeNos()` 负责：

1. 空数组直接返回，保持单人投标兼容。
2. 通过 `PersonnelClient::fetchAll()` 读取 Redis 缓存或外部人员接口。
3. 使用 `PersonnelUser::normalizeEmployeeNo()` 统一工号格式。
4. 阻止 OWNER 同时作为 COLLABORATOR。
5. 拒绝不在人员目录中的手工伪造工号。
6. 返回去重后的工号数组。

外部人员接口不可用且本次选择了协作者时，页面会收到中文字段错误：

```text
人员列表暂时不可用，无法校验协作成员，请稍后重试。
```

系统不会在无法确认人员真实性时写入联合投标。

## 9. 第四步：事务中写入统一成员模型

联合投标仍然只创建一条 `bid`。全部人员写入 `bid_member`：

```text
bid
└── bid_member OWNER          当前登录人，必须且只能一个
└── bid_member COLLABORATOR   协作者，可以有零到多个
```

核心写入结构：

```php
$members = [[
    'id' => $this->ids->next(),
    'bid_id' => $bid->id,
    'user_id' => $ownerEmployeeNo,
    'role' => 'OWNER',
    'created_at' => $now,
]];

foreach ($collaboratorEmployeeNos as $employeeNo) {
    $members[] = [
        'id' => $this->ids->next(),
        'bid_id' => $bid->id,
        'user_id' => $employeeNo,
        'role' => 'COLLABORATOR',
        'created_at' => $now,
    ];
}

// 使用一次批量 insert 写入同一投标的全部成员。
BidMember::query()->insert($members);
```

数据库的 `unique(bid_id, user_id)` 是最后一道保护。即使以后业务代码出现错误，同一投标也不能重复写入相同人员。

`BID_SUBMITTED` 的 `event_data` 同时记录：

```json
{
    "memberCount": 3,
    "collaboratorCount": 2
}
```

事件只保存必要审计快照，人员关系仍以 `bid_member` 为准。

## 10. 第五步：向 Inertia 页面提供人员目录

`TaskController::show()` 注入 `PersonnelClient`，但不把外部接口完整 JSON 直接传给 React。

后端只输出选择器需要的最小结构：

```ts
export type PersonnelOption = {
    employeeNo: string;
    displayName: string;
    departmentName: string | null;
};
```

人员目录只在以下情况加载：

- 当前用户可以投标，需要显示人员选择器。
- 当前任务已经有投标，需要把成员工号转换成姓名。

没有投标、当前人又不能投标时，不读取和传输大人员列表。

人员接口异常不会让任务详情整体报错。页面仍可以打开，已有历史成员退回显示工号；只是当前无法选择新的协作者。

## 11. 第六步：实现多人选择器

创建文件：

```text
resources/js/components/common/PersonnelMultiSelect.tsx
```

它具备以下行为：

- 按姓名、工号和部门做不区分大小写的模糊搜索。
- 输入停止约 300ms 后再过滤，降低大数组重复计算频率。
- 一次最多渲染 20 条结果。
- 已选成员显示为紫色轻量标签，可以单独移除。
- OWNER 工号通过 `excludedEmployeeNos` 排除。
- 不使用 Portal，直接在 Dialog 中间可滚动区域展开，避免浮层焦点冲突。

页面使用方式：

```tsx
<PersonnelMultiSelect
    disabled={form.processing}
    // 当前登录人会由后端写为 OWNER，不能再选为协作者。
    excludedEmployeeNos={[currentEmployeeNo]}
    onChange={(employeeNos) =>
        form.setData('collaboratorEmployeeNos', employeeNos)
    }
    options={personnelOptions}
    value={form.data.collaboratorEmployeeNos}
/>
```

选择器只返回工号数组，不保存姓名。姓名属于外部实时展示数据，真正的投标成员关系由数据库工号表达。

## 12. 第七步：详情页展示联合成员

投标卡片分别展示：

- 主投标人：姓名 + 工号。
- 协作成员：每人一个轻量标签。
- 没有协作者时显示“单人投标”。

`TaskController::bidItem()` 用人员目录把 `bid_member.user_id` 转换为展示名称。如果人员已离开目录或接口不可用，则使用工号兜底，历史业务记录不会因此消失。

## 13. 完整事务边界

本功能最终事务如下：

```text
事务外：
1. FormRequest 校验字段结构
2. 调用 PersonnelClient 校验协作者

事务内：
1. SELECT task ... FOR UPDATE
2. 再次校验任务为 OPEN、未截止、不是发布者本人
3. 校验 OWNER 没有其他 ACTIVE 投标
4. 创建 bid
5. 创建一个 OWNER bid_member
6. 创建零到多个 COLLABORATOR bid_member
7. 保存附件引用
8. 写入 BID_SUBMITTED task_event
9. 提交事务
```

网络调用放在事务外，数据一致性操作放在事务内。这与 Spring 中“不要在长事务中调用慢 RPC”的原则一致。

## 14. Laravel 与 Spring Boot 对照

| TaskHub / Laravel | Spring Boot 中近似概念 | 说明 |
| --- | --- | --- |
| `StoreBidRequest` | Bean Validation + Request DTO | Laravel 同时负责授权入口和校验消息 |
| `BidController` | `@RestController` / MVC Controller | 只组织 HTTP 输入输出 |
| `PlaceBidService` | `@Service` | 表达完整“提交投标”动作 |
| `DB::transaction()` | `@Transactional` | 闭包抛异常时自动回滚 |
| `PersonnelClient` | Feign Client / WebClient 封装 | 隔离外部接口原始结构 |
| Inertia Props | MVC Model / ViewModel | 服务端向 React 页面传递初始数据 |
| `useForm` | 前端表单状态对象 | 管理字段、提交中状态和后端校验错误 |

## 16. 常见错误

### 16.1 人员列表暂时不可用

检查：

```bash
php artisan config:clear
tail -f storage/logs/laravel.log
```

确认人员接口 URL、Redis/缓存配置和当前 Session accessToken 有效。不要把 accessToken 固定写入 `.env`。

### 16.2 候选列表为空

先确认 Redis 中已有成功同步的人员数据；如果没有缓存，当前请求会尝试使用登录人的动态 Token 调远程接口。

### 16.3 手工提交工号被拒绝

这是预期行为。前端隐藏和过滤只改善体验，真正的数据合法性必须由后端人员目录校验。

### 16.4 重复成员数据库错误

正常请求会被 FormRequest 的 `distinct` 和 Service 去重处理。如果仍触发 `unique(bid_id, user_id)`，说明存在绕过当前 Service 的写入代码，应检查调用链，而不是删除唯一约束。

## 18. 本章总结

本章没有新增“多人投标 JSON 字段”，而是使用已经确认的关系表设计：一个 `bid` 对应多条 `bid_member`。这种方式可以建立唯一约束、按成员查询投标，并能在后续选标时直接把中标成员复制到 `task_assignee`。
