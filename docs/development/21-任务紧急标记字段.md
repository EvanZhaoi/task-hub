# 21 - 任务紧急标记字段

## 1. 本章目标

本章记录 TaskHub 任务紧急标记的最终设计和实现。

最初方案将紧急度设计为 `LOW / MEDIUM / HIGH` 三级枚举。进一步确认业务需求后，TaskHub 当前只需要区分：

- 普通任务。
- 紧急任务。

因此最终使用独立布尔字段 `is_urgent`，不再保留三级紧急度。

## 2. 最终数据库设计

`task` 表新增字段：

```sql
`is_urgent` TINYINT(1) NOT NULL DEFAULT 0
  COMMENT '是否紧急：0 否 / 1 是'
```

字段含义：

| 数据库存储值 | PHP | TypeScript | 页面含义 |
| --- | --- | --- | --- |
| `0` | `false` | `false` | 普通任务 |
| `1` | `true` | `true` | 紧急任务 |

数据库增加 CHECK 约束：

```sql
CONSTRAINT `CHK_task_is_urgent`
  CHECK (`is_urgent` IN (0, 1))
```

MySQL 的 `BOOLEAN` 实际是 `TINYINT(1)` 的别名。这里在正式 SQL 中直接使用 `TINYINT(1)`，清楚表达实际存储类型。

默认值为 `0`，历史任务和没有特别标记的任务都按普通任务处理。

## 3. 与复杂度的关系

`complexity` 和 `is_urgent` 是两个独立字段：

| 字段 | 表达的问题 | 示例 |
| --- | --- | --- |
| `complexity` | 任务实现难度如何 | 简单、中等、复杂 |
| `is_urgent` | 是否需要优先关注 | 普通、紧急 |

复杂任务不一定紧急，紧急任务也可能很简单。因此不能继续使用 `complexity` 推导紧急状态。

## 4. 数据库升级方式

### 4.1 全新数据库

全新环境继续执行：

```text
database/schema.sql
```

最新完整建表脚本已经包含：

- `task.is_urgent`
- 默认值 `0`
- 中文字段注释
- `CHK_task_is_urgent` 约束

### 4.2 尚未增加过紧急度字段的已有数据库

如果数据库中既没有 `urgency`，也没有 `is_urgent`，执行一次：

```text
database/patches/20261014_add_task_is_urgent.sql
```

MySQL CLI 示例：

```bash
mysql -h 127.0.0.1 -P 3306 -u taskhub -p taskhub \
  < database/patches/20261014_add_task_is_urgent.sql
```

### 4.3 已经执行过旧版三级 urgency 脚本的数据库

如果数据库已经存在：

```text
urgency VARCHAR(20)
```

不要执行 `add_task_is_urgent.sql`，改为执行：

```text
database/patches/20261014_convert_task_urgency_to_boolean.sql
```

转换规则：

- 原 `HIGH` 转换为 `is_urgent = 1`。
- 原 `LOW`、`MEDIUM` 转换为 `is_urgent = 0`。
- 转换完成后删除旧 `urgency` 字段和 `CHK_task_urgency` 约束。

MySQL CLI 示例：

```bash
mysql -h 127.0.0.1 -P 3306 -u taskhub -p taskhub \
  < database/patches/20261014_convert_task_urgency_to_boolean.sql
```

两个增量脚本只能根据当前数据库状态选择一个，不能都执行。

### 4.4 执行前后检查

执行升级前先确认当前字段：

```sql
SHOW COLUMNS FROM `task` LIKE 'urgency';
SHOW COLUMNS FROM `task` LIKE 'is_urgent';
```

升级完成后检查：

```sql
SHOW COLUMNS FROM `task` LIKE 'is_urgent';

SELECT `id`, `title`, `complexity`, `is_urgent`
FROM `task`
ORDER BY `created_at` DESC
LIMIT 10;
```

本次没有为 `is_urgent` 单独创建索引。布尔字段区分度很低，并且当前没有紧急任务筛选查询，单列索引没有明确收益。

## 5. 后端实现

发布任务时，紧急标记经过以下链路：

```text
React 表单 isUrgent
    ↓
StoreTaskRequest boolean 校验
    ↓
CreateTaskService
    ↓
task.is_urgent
    ↓
TASK_CREATED event_data.isUrgent
```

### 5.1 请求校验

`StoreTaskRequest` 使用：

```php
'isUrgent' => ['required', 'boolean'],
```

发布表单无论是否勾选都会提交明确的布尔值，因此后端可以区分字段缺失和普通任务。

对应中文错误：

- 缺少字段：`请确认任务是否紧急。`
- 不是布尔值：`任务紧急标记格式不正确。`

### 5.2 保存任务

`CreateTaskService` 将 camelCase 请求字段转换为数据库 snake_case 字段：

```php
'is_urgent' => $validated['isUrgent'],
```

创建事件同步记录：

```php
'isUrgent' => $task->is_urgent,
```

### 5.3 Eloquent 类型转换

`Task` Model 的 `$fillable` 增加 `is_urgent`，并在 `casts()` 中声明：

```php
'is_urgent' => 'boolean',
```

这样数据库中的 `0/1` 在 PHP 业务代码中始终表现为 `false/true`，避免各处手工转换。

### 5.4 Inertia Props

`TaskController` 在任务大厅查询中选择 `is_urgent`，并统一向前端返回 camelCase：

```text
isUrgent: boolean
```

以下两个页面结构都包含该字段：

- `taskItem()`：任务大厅列表项。
- `taskDetail()`：任务详情数据。

## 6. 前端实现

### 6.1 发布任务表单

发布任务弹窗使用原生复选框表达二选一设置：

```text
☐ 紧急任务
```

交互规则：

- 默认不勾选，提交 `isUrgent = false`。
- 勾选后提交 `isUrgent = true`。
- 不再显示低、中、高下拉选项。

复选框适合表达布尔设置，比下拉框更直接，也符合用户对“是否紧急”的理解。

### 6.2 任务大厅

任务卡片只有在 `task.isUrgent === true` 时显示红色“紧急”徽标。

普通任务不显示“普通”徽标，避免每张卡片增加重复信息，使用户能够快速发现真正需要关注的任务。

### 6.3 任务详情

详情页同样只在紧急任务上显示“紧急”徽标。

复杂度徽标继续独立展示，不受紧急标记影响。

### 6.4 TypeScript 类型

`TaskListItem` 和 `TaskDetail` 使用：

```ts
isUrgent: boolean;
```

原来的 `TaskUrgency` 枚举类型已经删除，避免前端继续传递 `LOW / MEDIUM / HIGH`。

## 8. 部署顺序

已有环境按以下顺序操作：

1. 备份数据库。
2. 使用 `SHOW COLUMNS` 判断当前是否存在旧 `urgency` 字段。
3. 根据数据库现状选择一个增量脚本执行。
4. 确认最终只有 `is_urgent`，且值只有 `0/1`。
5. 发布最新后端和前端代码。
6. 发布普通任务和紧急任务各一条，检查列表与详情展示。

必须先完成数据库升级，再运行查询 `task.is_urgent` 的新代码，否则任务大厅会因字段不存在而报错。

## 10. 当前未增加的能力

本次只完成紧急标记的创建、保存和展示，没有增加：

- 只看紧急任务的筛选条件。
- 紧急任务优先排序。
- 根据截止时间自动标记紧急。
- 修改紧急标记的审批流程。
- `is_urgent` 专用数据库索引。

这些能力等出现明确需求后再增加，当前保持简单的布尔标记即可。
