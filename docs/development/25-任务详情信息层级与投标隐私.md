# 25 - 任务详情信息层级与投标隐私

## 1. 本章目标

本章优化任务大厅和详情页的信息层级，并修复投标时间线可能泄露他人投标履历的问题。

本次不修改数据库结构和投标业务流程，主要完成：

1. 任务大厅和详情页统一状态、复杂度、紧急情况的样式。
2. 预算和确定金额只显示一个，并明确当前金额的业务含义。
3. 投标记录改为摘要行加展开详情。
4. 无权查看他人投标时展示数量和隐私说明，不再显示成“无人投标”。
5. 投标列表和业务时间线使用一致的可见性规则。

## 2. 最终效果

### 2.1 任务属性

任务大厅和详情页都使用：

```text
[招标中] [复杂度：中等] [非紧急]
```

标签由同一个 `TaskAttributeBadges` 业务组件生成，避免两个页面分别维护颜色和文案。

### 2.2 金额

任务未确定最终金额时：

```text
任务预算
¥3,000.00
```

任务选标或后续业务已经确定金额时：

```text
确定金额
¥2,800.00
```

页面不会同时并列展示预算和最终金额。确定金额使用低饱和紫色，预算保持中性色，既能区分又不会过度突出。

### 2.3 投标记录

默认只显示一行重要信息：

```text
[有效投标]  主投标人  投标金额  承诺交付日期  [展开]
```

展开后显示：

- 投标版本和提交时间。
- 投标说明。
- 协作成员。
- 投标附件。

### 2.4 投标隐私

普通访问者不能查看他人的投标详情，但可以知道任务是否已有投标：

```text
该任务已有 3 条投标
投标详情仅对任务发布者和对应投标成员可见。
```

这比“暂无投标记录”更准确，同时不会泄露投标人、金额、方案和附件。

## 4. 统一任务属性标签

业务组件接收页面已经拥有的三个属性：

```tsx
type TaskAttributeBadgesProps = {
    complexity: TaskComplexity;
    displayStatus: TaskStatus;
    isUrgent: boolean;
};
```

页面只负责传值：

```tsx
{/* 列表页和详情页使用完全相同的任务属性组件。 */}
<TaskAttributeBadges
    complexity={task.complexity}
    displayStatus={task.displayStatus}
    isUrgent={task.isUrgent}
/>
```

该组件属于 `components/tasks`，而不是 `components/ui`。原因是它知道 TaskStatus 和 TaskComplexity，已经包含 TaskHub 业务语义；基础 Badge 仍保持通用。

## 5. 金额展示规则

后端增加展示字段：

```php
[
    // amountLabel 始终只格式化当前应该展示的一个金额。
    'amountLabel' => $this->amountLabel($task),
    // final_amount 存在时，页面需要明确告诉用户这是已经确定的金额。
    'amountType' => $task->final_amount === null ? 'BUDGET' : 'FINAL',
]
```

前端类型：

```ts
// BUDGET 表示发布预算，FINAL 表示已经确定的金额。
amountType: 'BUDGET' | 'FINAL';
```

这种方式没有让前端通过任务状态猜测金额含义。真正的数据规则由后端决定，React 只决定文字和颜色。

## 6. 投标折叠设计

`BidList` 在页面内使用 `expandedBidIds` 保存展开状态：

```tsx
const [expandedBidIds, setExpandedBidIds] = useState<string[]>([]);

/**
 * 每条投标独立展开，不影响其他记录。
 */
function toggleBid(bidId: string): void {
    setExpandedBidIds((currentIds) =>
        currentIds.includes(bidId)
            ? currentIds.filter((currentId) => currentId !== bidId)
            : [...currentIds, bidId],
    );
}
```

这里没有建立公共 Hook，因为展开状态只服务当前一个业务组件，尚不存在跨页面复用需求。

“选择该方案”按钮位于展开按钮外部，避免在一个 `<button>` 内嵌套另一个交互按钮。这样键盘操作和浏览器点击行为更可靠。

## 7. 投标可见性摘要

后端返回：

```php
'bidOverview' => [
    // 数据库中该任务的全部投标记录数量。
    'totalCount' => $totalBidCount,
    // 当前用户实际有权查看的投标数量。
    'visibleCount' => count($visibleBids),
    // 只用于告诉用户存在隐藏记录，不包含任何方案详情。
    'hiddenCount' => max(0, $totalBidCount - count($visibleBids)),
],
```

权限规则：

| 用户 | 可见投标 |
| --- | --- |
| 任务发布者 | 当前任务全部投标 |
| 投标 OWNER | 自己参与的投标 |
| 投标 COLLABORATOR | 自己参与的投标 |
| 其他用户 | 只看到投标数量和隐私说明 |

前端隐藏不是权限控制。`visibleBids` 本身已经由后端过滤，浏览器不会收到无权查看的报价、成员、说明或附件。

## 8. 业务时间线权限

需要保护的投标事件包括：

```php
private const PRIVATE_BID_EVENT_TYPES = [
    'BID_SUBMITTED',
    'BID_WITHDRAWN',
    'BID_ACCEPTED',
];
```

可见性与投标列表一致：

- 发布者看到全部投标事件。
- 投标成员只看到与自己可见 Bid 关联的事件。
- 其他访问者看不到任何个人投标事件。
- `TASK_CREATED`、`TASK_PUBLISHED`、`TASK_ASSIGNED` 等任务生命周期事件继续显示。

过滤必须发生在 Laravel 查询中，不能把全部事件传到 React 后再隐藏。否则敏感信息仍会出现在 Inertia JSON、浏览器开发者工具和网络响应中。

## 9. 人员目录加载优化

之前只要任务存在投标，详情页就会加载全员人员目录。隐私调整后改为仅在以下情况加载：

1. 当前用户可以投标，需要协作者选择器。
2. 当前用户有权查看投标成员。
3. 任务已有正式执行成员，需要展示姓名。

无关用户只看投标数量时，不再为了隐藏的投标请求和转换全员数据。

## 10. 验证步骤

在项目根目录执行：

```bash
# 检查 TypeScript 类型和 JSX。
npm run typecheck

# 验证生产构建。
npm run build

# 验证后端投标权限、金额类型和详情 Props。

```

手工检查：

1. 打开未选标任务，列表和详情都显示“任务预算”。
2. 选标后重新打开，列表和详情都显示“确定金额”。
3. 对比列表与详情的状态、复杂度、紧急标签，确认样式一致。
4. 发布者打开任务，确认可以展开全部投标。
5. 投标成员打开任务，确认只能看到自己参与的投标。
6. 无关用户打开任务，确认能看到投标总数但看不到任何投标详情。
7. 无关用户查看时间线，确认没有他人的投标提交、撤回或中标记录。

## 11. 常见错误

### 11.1 页面仍显示“暂无投标”

检查详情接口是否返回 `bidOverview.totalCount`。空列表只说明当前用户没有可见投标，不等于数据库没有投标。

### 11.2 时间线隐藏了所有事件

只应过滤 `PRIVATE_BID_EVENT_TYPES`。任务发布、指派、完成、取消和流标等任务级事件不应被一起排除。

### 11.3 列表和详情标签颜色不同

检查两个页面是否都使用 `TaskAttributeBadges`，不要在页面内重新建立状态颜色映射。

### 11.4 金额标题不正确

检查 `final_amount` 是否为空。标题不应由前端根据 `status` 自行推断。

## 12. 本章总结

本次优化不仅减少了页面占用空间，还统一了信息语义和权限边界。尤其需要记住：如果一类业务数据在主列表中受权限保护，那么时间线、统计接口和 Inertia Props 也必须使用相同的权限规则，不能从其他展示入口间接泄露。
