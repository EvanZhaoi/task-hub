# 19-剩余功能优先级与实现设想

## 本章目标

本章用于集中记录 TaskHub 从当前状态到 MVP 可用版本还需要完成的功能，并按优先级说明每个功能的用户操作方式、页面显示方式和后端逻辑设计。

当前第一目标是尽快把系统做出来，因此后续开发应优先完成核心业务闭环：

```text
发布任务
↓
开发者投标
↓
发布者选标
↓
开发者交付
↓
发布者验收
↓
任务完成
```

## 当前已完成基础

以下能力已经具备，后续功能应直接复用，不重新设计：

| 类别 | 已完成内容 | 说明 |
| --- | --- | --- |
| 基础架构 | Laravel + React + Inertia | 单体架构，页面由 Laravel 返回 Inertia，由 React 渲染。 |
| 认证 | SSO 授权码模式 | 登录后保存当前用户信息，后端使用动态 accessToken 调总部接口。 |
| 外部接口 | 当前人员、人员列表、付款账号、文件上传 | 外部接口统一放在 Integrations 下，不在 Controller 中直接处理原始 JSON。 |
| 角色 | 数据库角色控制 | 当前已支持 TOP 角色扩展，不再依赖环境变量控制业务角色。 |
| 任务大厅 | 任务列表、筛选、发布任务入口 | 首页已经具备任务大厅雏形。 |
| 发布任务 | 模态框发布、富文本描述、附件上传 | 附件保存 id 和 name，任务描述保存 HTML 并做后端白名单清洗。 |
| 数据模型 | Task、Bid、BidMember、TaskAssignee、TaskDelivery、AttachmentRef、TaskChangeRequest、TaskEvent | 数据库结构以 database/schema.sql 为准。 |

## 优先级说明

| 优先级 | 含义 |
| --- | --- |
| P0 | MVP 必须完成，不完成系统无法形成核心业务闭环。 |
| P1 | MVP 建议完成，影响真实使用体验或关键边界流程。 |
| P2 | 后续增强功能，不阻塞第一版上线试用。 |

## P0-1 任务详情页

### 状态

未完成。

### 为什么优先做

当前任务大厅只能看到任务卡片，用户无法进入某个任务查看完整描述、附件、投标、交付、变更和事件时间线。后续投标、选标、交付都需要依附于任务详情页。

### 用户操作方式

1. 用户在任务大厅点击某个任务卡片或“查看详情”按钮。
2. 系统进入任务详情页。
3. 页面根据当前用户身份和任务状态展示可用操作。

### 页面显示方式

建议任务详情页采用三段式布局：

```text
顶部：任务标题、状态、预算、交付日期、发布人、付款账号
中部左侧：任务描述、附件、交付内容
中部右侧：操作区、投标列表、当前用户投标状态
底部：TaskEvent 时间线
```

任务描述使用 `RichTextViewer` 展示，不直接渲染未经处理的 HTML。

附件展示已保存的 `attachment_name`，后续下载或预览时再使用 `attachment_id`。

### 后端逻辑设计

新增任务详情查询时，Controller 只负责：

```text
接收 task id
↓
查询 Task 及相关展示数据
↓
组装 Inertia Props
↓
返回 React 页面
```

如果只是查询展示，可以暂时放在 Controller 中；如果详情组装逻辑明显变复杂，再抽 `ShowTaskService` 或 `TaskDetailQueryService`。

### 涉及文件设想

| 文件 | 作用 |
| --- | --- |
| `routes/web.php` | 增加 `GET /tasks/{task}`。 |
| `app/Http/Controllers/TaskController.php` | 增加 `show()` 方法。 |
| `resources/js/Pages/Tasks/Show.tsx` | 任务详情页。 |
| `resources/js/components/tasks/TaskDetailHeader.tsx` | 任务详情头部。 |
| `resources/js/components/tasks/TaskEventTimeline.tsx` | 任务事件时间线。 |

## P0-2 投标功能

### 状态

未完成。

### 用户操作方式

1. 开发者进入任务详情页。
2. 当任务状态为 `OPEN` 且未超过 `bidding_deadline` 时，显示“我要投标”按钮。
3. 点击后打开投标弹窗。
4. 用户填写投标金额、预计交付日期、投标说明，可选择协作者和附件。
5. 提交后页面显示“已投标”状态。

### 页面显示方式

投标使用模态框，不单独做页面。

字段建议：

| 字段 | 说明 |
| --- | --- |
| 投标金额 | `decimal(18,2)`，不能高于或低于规则后续由产品确认。 |
| 预计交付日期 | 日期选择器。 |
| 投标说明 | 可先使用普通 textarea，后续再考虑富文本。 |
| 协作者 | 人员选择器，数据来自人员列表缓存。 |
| 附件 | 复用现有附件上传。 |

### 后端逻辑设计

投标属于完整业务动作，应使用 Service：

```text
PlaceBidService
↓
开启数据库事务
↓
校验 Task 为 OPEN
↓
校验当前时间未超过 bidding_deadline
↓
校验当前 OWNER 没有 ACTIVE 投标
↓
创建 Bid
↓
创建 OWNER BidMember
↓
创建 COLLABORATOR BidMember
↓
保存投标附件 AttachmentRef
↓
写入 BID_SUBMITTED TaskEvent
↓
提交事务
```

### 注意事项

`bid.active_key` 由 `task_id:OWNER工号` 组成，只在 `ACTIVE` 状态时非空，用于限制同一任务同一 OWNER 只能有一条有效投标。

## P0-3 撤回投标与重新投标

### 状态

未完成。

### 用户操作方式

1. 开发者进入任务详情页。
2. 如果当前用户已有 `ACTIVE` 投标，且任务未截止，显示“撤回投标”。
3. 撤回后可以重新投标。

### 页面显示方式

撤回使用确认弹窗：

```text
确认撤回当前投标？
撤回后该投标会保留为历史记录，未截止前可以重新投标。
```

### 后端逻辑设计

撤回投标使用 `WithdrawBidService`：

```text
开启事务
↓
校验任务未超过 bidding_deadline
↓
校验 Bid 为 ACTIVE
↓
校验操作者是 OWNER
↓
Bid 改为 WITHDRAWN
↓
active_key 置为 NULL
↓
写入 BID_WITHDRAWN TaskEvent
↓
提交事务
```

## P0-4 选标功能

### 状态

未完成。

### 用户操作方式

1. 发布者进入任务详情页。
2. 查看所有有效投标。
3. 点击某个投标的“选为中标”。
4. 系统弹出确认框。
5. 确认后任务进入进行中。

### 页面显示方式

任务详情页右侧显示投标列表。

每个投标卡片展示：

| 内容 | 说明 |
| --- | --- |
| 主投标人 | 来自 BidMember OWNER。 |
| 协作者 | 来自 BidMember COLLABORATOR。 |
| 投标金额 | Bid 金额。 |
| 预计交付 | Bid 交付日期。 |
| 投标说明 | Bid 描述。 |
| 附件 | 投标附件。 |

### 后端逻辑设计

选标必须使用 `SelectBidService`，并控制事务：

```text
锁定 Task
↓
校验 Task 为 OPEN
↓
校验目标 Bid 为 ACTIVE
↓
目标 Bid 改为 ACCEPTED，active_key 置 NULL
↓
其他 ACTIVE Bid 改为 LOST，active_key 置 NULL
↓
Task 改为 ASSIGNED
↓
写入 assigned_bid_id
↓
设置 primary_assignee_id 为 BidMember OWNER 的工号
↓
BidMember 复制到 TaskAssignee
↓
Task version 递增
↓
写入 BID_ACCEPTED 和 TASK_ASSIGNED
↓
提交事务
```

## P0-6 提交交付

### 状态

未完成。

### 用户操作方式

1. 负责人进入任务详情页。
2. 当任务状态为 `ASSIGNED` 时，显示“提交交付”按钮。
3. 点击后打开交付弹窗。
4. 填写交付说明，上传附件。
5. 提交后等待发布者验收。

### 页面显示方式

交付使用模态框。

字段建议：

| 字段 | 说明 |
| --- | --- |
| 交付说明 | textarea 或富文本。 |
| 附件 | 复用附件上传。 |

### 后端逻辑设计

使用 `SubmitDeliveryService`：

```text
开启事务
↓
校验 Task 为 ASSIGNED
↓
校验操作者是 TaskAssignee OWNER 或允许提交的成员
↓
创建 TaskDelivery
↓
Phase 1 固定 delivery_no = 1
↓
保存交付附件 AttachmentRef
↓
写入 DELIVERY_SUBMITTED TaskEvent
↓
提交事务
```

### 重要规则

数据库支持多次交付，但 Phase 1 只允许一次交付，不增加 `unique(task_id)`，该限制由业务层控制。

## P0-7 验收交付与要求修改

### 状态

未完成。

### 用户操作方式

1. 发布者进入任务详情页。
2. 查看开发者提交的交付内容。
3. 可以点击“验收通过”或“要求修改”。
4. 要求修改时必须填写原因。

### 页面显示方式

交付区展示：

```text
交付说明
附件
提交人
提交时间
当前状态
验收操作按钮
```

### 后端逻辑设计

验收通过使用 `ReviewDeliveryService`：

```text
开启事务
↓
锁定 Task 和 TaskDelivery
↓
校验 Delivery 为 SUBMITTED
↓
Delivery 改为 ACCEPTED
↓
Task 改为 COMPLETED
↓
Task version 递增
↓
写入 DELIVERY_ACCEPTED 和 TASK_COMPLETED TaskEvent
↓
提交事务
```

要求修改：

```text
Delivery 改为 REVISION_REQUIRED
↓
Task 保持 ASSIGNED
↓
写入 REVISION_REQUIRED TaskEvent
```

## P1-1 招标截止自动流标

### 状态

未完成。

### 用户操作方式

用户不直接操作，由系统定时处理。

### 后端逻辑设计

使用 Laravel Scheduler：

```text
每分钟扫描
OPEN && bidding_deadline <= now()
↓
如果不存在 ACTIVE Bid
↓
调用 ExpireOpenTasksService
↓
Task 改为 FAILED
↓
Task version + 1
↓
写入 TASK_FAILED
```

不要为每个任务单独创建 Cron。

任务必须幂等处理，重复执行不应造成重复失败或重复事件。

## P1-4 变更与取消申请

### 状态

未完成。

### 用户操作方式

任务进入 `ASSIGNED` 后，双方可以发起变更或取消申请。

变更可以修改：

```text
finalAmount
finalDelivery
description
```

取消只允许把任务状态改为 `CANCELLED`。

### 页面显示方式

任务详情页增加“申请变更”和“申请取消”入口。

待审批申请展示在任务详情页明显位置。

### 后端逻辑设计

使用 `TaskChangeRequest`。

发起申请：

```text
创建 task_change_request
↓
request_type = CHANGE 或 CANCEL
↓
保存 base_task_version
↓
保存 old_value 和 new_value
↓
写入 CHANGE_REQUESTED TaskEvent
```

审批通过：

```text
锁定 Task 和 ChangeRequest
↓
校验 task.version == base_task_version
↓
应用 CHANGE 或 CANCEL
↓
Task version 递增
↓
ChangeRequest 改为 APPROVED
↓
写入 CHANGE_APPROVED 或 TASK_CANCELLED
```

## 建议开发顺序

为了最快形成可测试系统，建议按以下顺序推进：

```text
1. 任务详情页
2. 投标
3. 撤回投标
4. 选标
5. 任务参与人展示
6. 提交交付
7. 验收交付 / 要求修改
8. TaskEvent 时间线
9. 自动流标
10. 主动流标 / 延长截止
11. 变更与取消申请
12. 我的任务
13. 附件下载
```

其中 1 到 8 完成后，TaskHub 就具备第一版核心业务闭环。

## 下一步建议

下一步建议直接开发：

```text
任务详情页 + 投标入口
```

原因：

1. 任务详情页是后续所有业务操作的承载页面。
2. 投标是发布任务之后的第一个核心动作。
3. 做完后可以立刻从浏览器验证：

```text
发布任务
↓
进入详情
↓
查看完整内容
↓
提交投标
```
