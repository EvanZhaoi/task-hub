# 26 - 直接指定成员发布任务

## 1. 本章目标

本章完成 TaskHub 第一期的第二条任务创建路径：发布者不经过投标和选标，直接指定任务负责人和协作成员。

最终两种发布方式如下：

```text
招标选标：发布 -> OPEN -> 投标 -> 选标 -> ASSIGNED
直接指派：发布并选择成员 -> ASSIGNED
```

直接指派不是“由系统替发布者创建一条中标 Bid”。它不会生成 `bid` 和 `bid_member`，而是直接写入正式执行成员表 `task_assignee`。

## 2. 学习目标

完成本章后，应能理解：

1. 一个发布表单如何根据 `assignmentType` 切换字段和后端流程。
2. 为什么 Controller 只做流程分发，而不把两套事务写在一个方法中。
3. 为什么外部人员查询应放在数据库事务外。
4. `TaskAssignee` 为什么是正式执行成员的数据来源。
5. 前端隐藏字段为什么不能代替后端校验。

## 3. 最终效果

发布任务弹窗顶部提供两种模式：

```text
[招标选标] [直接指派]
```

选择“直接指派”后：

- 隐藏招标截止时间。
- 必须选择一名任务负责人。
- 可以选择零到多名协作成员。
- 负责人不能同时出现在协作成员中。
- 发布按钮显示“发布并指派”。
- 发布成功后任务直接显示为“进行中”。

数据库结果：

```text
task.status = ASSIGNED
task.assignment_type = DIRECT
task.assigned_bid_id = null
task.primary_assignee_id = 负责人 工号
task.final_amount = task.budget
task.final_delivery = task.expected_delivery
```

并写入：

```text
task_assignee：一个 OWNER，零到多个 COLLABORATOR
task_event：TASK_CREATED、TASK_ASSIGNED
attachment_ref：本次发布的附件引用
```

## 6. 第一步：扩展请求字段

前端提交的新增字段：

```ts
type TaskCreateForm = {
    // BIDDING 进入招标；DIRECT 直接产生正式执行成员。
    assignmentType: 'BIDDING' | 'DIRECT';
    // DIRECT 模式必填一个负责人，字段值是人员工号。
    ownerEmployeeNo: string;
    // DIRECT 模式可选多个协作成员，数组元素也是工号。
    collaboratorEmployeeNos: string[];
};
```

对应后端核心校验：

```php
return [
    // 只接受数据库和业务已经确认的两种发布方式。
    'assignmentType' => ['required', 'string', Rule::in(['BIDDING', 'DIRECT'])],

    // 直接指派不需要截止时间，exclude_if 会把该字段排除出 validated 数据。
    'biddingDeadline' => [
        'exclude_if:assignmentType,DIRECT',
        'required',
        'date',
        'after:now',
    ],

    // 负责人只属于 DIRECT 模式，并且必须选择一个工号。
    'ownerEmployeeNo' => [
        'exclude_unless:assignmentType,DIRECT',
        'required',
        'string',
        'max:32',
    ],

    // 协作成员允许为空，但限制最多 20 人并阻止数组内重复。
    'collaboratorEmployeeNos' => [
        'exclude_unless:assignmentType,DIRECT',
        'nullable',
        'array',
        'max:20',
    ],
    'collaboratorEmployeeNos.*' => ['required', 'string', 'max:32', 'distinct'],
];
```

FormRequest 只验证请求结构。某个工号是否真实存在、负责人是否又出现在协作者中，属于业务规则，由 `CreateDirectTaskService` 使用实时人员目录再次确认。

## 7. 第二步：为发布页提供人员选项

`TaskController@index` 已经负责组装任务大厅 Props，因此在同一个响应中增加最小人员选项：

```php
return Inertia::render('Tasks/Index', [
    // 付款账号仍用于两种发布模式。
    'paymentAccountOptions' => $this->paymentAccountOptions(
        $paymentAccounts,
        $currentUser->accessToken(),
    ),

    // 浏览器只收到工号、姓名和部门，不接收外部接口完整原始数据。
    'personnelOptions' => $this->personnelDirectory(
        $personnel,
        $currentUser->accessToken(),
    )['options'],
]);
```

人员 Client 使用当前 Session 中动态 accessToken，并复用已有 Redis 缓存。没有把 token 或外部接口地址暴露给 React。

## 8. 第三步：复用人员选择器

负责人是单选，协作者是多选，但搜索、候选展示和已选标签完全相同。因此保留一个 `PersonnelMultiSelect`，通过 `maxSelections` 控制最大数量：

```tsx
<PersonnelMultiSelect
    // 负责人最多只能选择一人。
    maxSelections={1}
    onChange={(employeeNos) => {
        // 单选模式取数组第一项；清空选择时回到空字符串。
        const ownerEmployeeNo = employeeNos[0] ?? '';

        form.setData({
            ...form.data,
            ownerEmployeeNo,
            // 负责人不能同时作为协作者，切换负责人时同步剔除重复工号。
            collaboratorEmployeeNos: form.data.collaboratorEmployeeNos.filter(
                (employeeNo) => employeeNo !== ownerEmployeeNo,
            ),
        });
    }}
    options={personnelOptions}
    value={form.data.ownerEmployeeNo ? [form.data.ownerEmployeeNo] : []}
/>
```

协作成员选择器则排除当前负责人：

```tsx
<PersonnelMultiSelect
    excludedEmployeeNos={
        form.data.ownerEmployeeNo ? [form.data.ownerEmployeeNo] : []
    }
    onChange={(employeeNos) =>
        form.setData('collaboratorEmployeeNos', employeeNos)
    }
    options={personnelOptions}
    value={form.data.collaboratorEmployeeNos}
/>
```

前端排除重复人员是体验优化。恶意请求可以绕过 React，所以 Service 仍必须执行相同的后端规则。

## 9. 第四步：Controller 分发业务动作

Controller 不创建 Task，也不控制事务，只选择业务 Service：

```php
$validated = $request->validated();

// 两种发布方式有不同状态流转，分别交给语义明确的 Service。
$service = $validated['assignmentType'] === 'DIRECT'
    ? $createDirectTask
    : $createTask;

$service->execute(
    validated: $validated,
    attachments: $request->attachments(),
    user: $currentUser->user(),
    accessToken: $currentUser->accessToken(),
);
```

这里没有新建泛化的 `TaskService`。`CreateTaskService` 表达招标发布，`CreateDirectTaskService` 表达直接指派，打开任一文件都能按顺序读懂完整动作。

## 10. 第五步：实现直接指派事务

完整流程：

```text
清洗任务描述 HTML
    ↓
使用动态 token 查询付款账号
    ↓
使用动态 token 查询人员目录
    ↓
校验 OWNER 和 COLLABORATOR
    ↓
开始数据库事务
    ↓
创建 ASSIGNED Task
    ↓
创建 TaskAssignee
    ↓
保存 AttachmentRef
    ↓
写 TASK_CREATED / TASK_ASSIGNED
    ↓
提交事务
```

外部接口查询位于事务外。原因是网络请求可能很慢或超时，如果在事务内等待，会延长数据库锁和连接占用时间。

事务入口：

```php
public function execute(
    array $validated,
    array $attachments,
    SsoUser $user,
    string $accessToken,
): void {
    // 富文本始终由后端白名单清洗，不能信任浏览器 HTML。
    $validated['description'] = $this->richTextSanitizer->clean(
        $validated['description'] ?? null,
    );

    // 外部查询放在事务外，避免持有数据库事务等待网络。
    $paymentAccount = $this->paymentAccounts->fetchById(
        (string) $validated['paymentAccountId'],
        $accessToken,
    );
    $members = $this->resolveMembers($validated, $accessToken);

    DB::transaction(function () use (
        $attachments,
        $members,
        $paymentAccount,
        $user,
        $validated,
    ): void {
        $task = $this->createTask(
            $validated,
            $paymentAccount,
            $user,
            $members['owner']->employeeNo(),
        );

        $this->saveAssignees($task, $members['owner'], $members['collaborators']);
        $this->saveAttachments($task, $attachments, $user);
        $this->createEvents(
            $task,
            $user,
            count($members['collaborators']),
            count($attachments),
        );
    });
}
```

## 11. 状态与事件设计

直接指派创建后立即可以执行，因此初始状态是 `ASSIGNED`。第一期不增加“等待被指派人确认”状态，也不创建无业务含义的 Bid。

事件：

| 事件 | 作用 |
| --- | --- |
| `TASK_CREATED` | 记录任务首次进入系统及发布快照 |
| `TASK_ASSIGNED` | 记录负责人、协作人数和附件数量 |

Task 当前状态仍以 `task.status` 为准，`task_event` 只用于详情时间线和审计，不用于事件溯源或状态重建。

## 12. 与 Spring Boot 的概念对照

| Laravel | Spring Boot 中相近概念 | 说明 |
| --- | --- | --- |
| `StoreTaskRequest` | `@Valid` Request DTO | Laravel 同时提供授权入口和校验消息 |
| `TaskController@store` | Controller 方法 | 只处理 HTTP 上下文和流程分发 |
| `CreateDirectTaskService` | `@Service` | 表达完整的直接指派业务动作 |
| `DB::transaction()` | `@Transactional` | 闭包抛异常时整体回滚 |
| Eloquent `Task::create()` | JPA Repository/Entity 持久化 | TaskHub 不额外增加 Repository 层 |
| Inertia Props | MVC Model / ViewModel | 后端直接向 React 页面传递序列化数据 |

Laravel 的 Eloquent 已经同时承担 Active Record 和查询构造能力，因此当前项目不再包一层 Repository。

## 14. 常见错误

### 14.1 人员列表暂不可用

现象：直接指派模式无法选择人员，发布按钮不可用。

排查：

1. 检查当前 Session 是否包含有效 accessToken。
2. 查看 `storage/logs/laravel.log` 中人员接口日志。
3. 检查 Redis 中是否已有最近一次成功的人员列表缓存。
4. 不要在前端硬编码工号绕过人员接口。

### 14.2 负责人同时出现在协作成员

前端会自动排除，但后端仍会返回中文校验错误。不要删除 Service 中的二次校验。

### 14.3 DIRECT 仍要求招标截止时间

确认 FormRequest 使用 `exclude_if:assignmentType,DIRECT`，并确认前端提交了正确的 `assignmentType`。

### 14.4 任务已创建但没有执行成员

正常实现中不会出现。Task 和 TaskAssignee 位于同一个 `DB::transaction()`；成员写入失败时 Task 也会回滚。

## 16. 本章总结

本章没有推翻原有发布流程，而是为 DIRECT 模式增加独立业务动作。页面复用人员选择器，Controller 负责分发，Service 负责人员校验和事务。数据库已有字段足以支持该流程，因此没有修改 Schema。
