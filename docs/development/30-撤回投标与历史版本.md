# 30 - 撤回投标与历史版本

## 1. 本章目标

本章记录 TaskHub 第一期“撤回投标”功能的实际实现。完成后，主投标人可以在招标截止前撤回自己的有效投标，并在截止前提交新版本；旧投标不会被覆盖，而是作为业务历史保留。

本功能不修改数据库结构。`database/schema.sql` 已经具备：

- `bid.status = WITHDRAWN`
- `bid.active_key`
- `bid.withdrawn_at`
- `bid.revision_no`
- `task_event.event_type = BID_WITHDRAWN`

## 2. 业务规则

撤回必须同时满足：

1. Task 状态是 `OPEN`。
2. 当前时间早于 `bidding_deadline`。
3. Bid 属于 URL 中的 Task。
4. Bid 状态是 `ACTIVE`。
5. 当前用户是 `bid_member.role = OWNER` 的主投标人。

协作成员可以查看共同投标，但不能代表 OWNER 撤回整个方案。发布者也不能替投标人撤回。

撤回成功后：

```text
bid.status       = WITHDRAWN
bid.active_key   = NULL
bid.withdrawn_at = 当前时间
```

`active_key` 清空后，同一任务和 OWNER 可以再次创建新的 `ACTIVE` 投标。新投标的 `revision_no` 在历史最大值上加一，原记录不会更新或删除。

## 4. 请求流程

```text
主投标人点击“撤回投标”
    ↓
WithdrawBidDialog 提交 POST 请求
    ↓
WithdrawBidRequest 校验 HTTP 参数
    ↓
BidController::withdraw()
    ↓
WithdrawBidService::execute()
    ↓
锁定 Task，再锁定 Bid
    ↓
校验归属、状态、截止时间和 OWNER 身份
    ↓
更新 Bid 并写入 BID_WITHDRAWN
    ↓
提交事务并返回任务详情
```

Controller 不直接修改 Model。撤回涉及两张业务表和完整状态判断，因此按照项目规范使用独立的动作型 Service。

## 5. 为什么要在事务内重新校验

页面上的 `canWithdraw` 只负责决定是否显示按钮，不能保证提交请求时数据仍未变化。例如，用户打开页面后，发布者可能已经完成选标，或者招标时间已经截止。

因此 `WithdrawBidService` 按以下顺序处理：

```php
// 先锁定任务，避免与选标、流标同时修改任务状态。
$lockedTask = Task::query()
    ->whereKey($task->id)
    ->lockForUpdate()
    ->firstOrFail();

// 再锁定投标，避免同一投标被重复撤回或同时选中。
$lockedBid = Bid::query()
    ->whereKey($bid->id)
    ->lockForUpdate()
    ->firstOrFail();
```

锁定顺序与 `SelectBidService` 保持一致，可以降低并发事务死锁风险。即使用户重复点击，第二次请求也会读到 `WITHDRAWN` 并返回中文业务错误，不会重复写事件。

## 6. 历史投标展示

任务详情将当前用户有权看到的投标分为两组：

- **有效投标**：只包含 `ACTIVE`。
- **历史投标**：包含 `WITHDRAWN`、`ACCEPTED` 和 `LOST`，默认折叠。

发布者可以看到该任务的全部投标历史；普通用户只能看到自己参与的记录。其他用户只能看到当前有效投标数量，不会收到撤回历史数量、报价、成员、附件等隐私数据。

已撤回投标：

- 不计入 `activeBidCount`，也不计入任务列表显示的投标数量。
- 不能参与选标。
- 不显示撤回按钮。
- 展开后显示提交时间和撤回时间。
- 仍保留原说明、成员和附件，供本人和发布者审计。

## 7. 与 Spring Boot 的概念对照

| Laravel | Spring Boot 中的近似概念 |
| --- | --- |
| Route | `@PostMapping` |
| FormRequest | 请求 DTO + Bean Validation + 一部分 HTTP 授权入口 |
| Controller | `@RestController` / MVC Controller |
| Service | `@Service` 业务动作 |
| `DB::transaction()` | `@Transactional` |
| `lockForUpdate()` | JPA PESSIMISTIC_WRITE / `SELECT ... FOR UPDATE` |
| ValidationException | 业务校验异常并回填表单错误 |

这里的对应关系不是完全相同。Laravel FormRequest 会在进入 Controller 前自动执行，而业务状态校验仍放在 Service 中，因为它需要事务锁定后的最新数据。

## 8. 验证内容

自动化测试覆盖：

- OWNER 正常撤回。
- `status`、`active_key` 和 `withdrawn_at` 正确更新。
- `BID_WITHDRAWN` 只写一次。
- 重复撤回被拒绝。
- COLLABORATOR 不能撤回。
- 截止后不能撤回。
- 撤回后可以提交第 2 版投标。
- 旧版本和新版本同时保留。
- 详情接口返回有效投标与已撤回历史。

## 9. 本章完成效果

撤回投标已经形成完整闭环：

```text
有效投标 → OWNER 确认撤回 → 保留历史 → 释放 active_key → 提交新版本
```

下一项第一期功能是招标截止定时任务，负责区分“待选标”和“自动流标”，并向任务发布者发送对应邮件。
