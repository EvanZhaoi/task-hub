# 13-开发任务清单

## 本章目标

本章是 TaskHub 当前阶段的项目任务总表，用来回答三个问题：

1. 当前仓库已经完成了什么。
2. 后续还剩哪些功能没有完成。
3. 下一步应该按什么顺序继续开发。

这不是需求文档，也不是数据库设计文档。需求文档说明“系统应该做什么”，数据库设计文档说明“数据怎么存”，本章只记录“开发进度和剩余任务”。

## 状态说明

| 状态 | 含义 |
|---|---|
| 已完成 | 当前仓库已有可运行代码、配置、测试或文档支撑，可以继续在其上开发 |
| 部分完成 | 已有基础结构、数据库或文档，但完整业务流程还没有实现 |
| 未完成 | 当前仓库还没有正式实现 |
| 待确认 | 需要产品负责人、总部接口方或业务方确认后才能开发 |
| 暂不做 | 已明确不属于当前 MVP 或当前阶段范围 |

## 当前真实进度总览

当前已经完成的主链路：

```text
Laravel + React + Inertia 基础项目
↓
SSO 授权码登录和退出
↓
当前登录人 Session
↓
TaskHub 本地角色读取
↓
任务大厅列表
↓
发布招标任务
↓
记录任务附件 ID
↓
写入任务发布事件
```

当前还没有完成的主链路：

```text
任务详情
↓
投标
↓
撤回投标
↓
选标
↓
任务执行成员
↓
提交交付
↓
验收 / 要求修改
↓
任务变更 / 取消审批
↓
流标 / 延长招标截止
↓
我的任务 / TOP 视图
```

## 建议开发顺序

### 第一组：先整理发布任务边界

1. 新增 `CreateTaskService`。
2. 把 `TaskController::store()` 中的发布任务事务移入 Service。
3. 保持路由、前端和数据库不变。
4. 补充测试，确认发布任务行为不变。

这样做的原因：后续投标、选标、交付都会按“Controller 调 Service”的规范开发。先把发布任务整理好，可以作为后续业务 Service 的模板。

### 第二组：打通任务详情和投标

1. 做任务详情页。
2. 做投标模态框。
3. 做 `PlaceBidService`。
4. 做投标列表权限展示。
5. 做撤回投标。

这样做的原因：发布任务已经完成，任务进入 `OPEN` 后最自然的下一步就是有人投标。

### 第三组：完成招标闭环

1. 做选标。
2. 中标成员复制到执行成员。
3. 任务进入 `ASSIGNED`。
4. 详情页展示执行成员和中标信息。

这样做的原因：选标完成后，TaskHub 才真正从“任务发布平台”进入“任务撮合平台”。

### 第四组：完成执行闭环

1. 做提交交付。
2. 做验收通过。
3. 做要求修改。
4. 做任务完成。

这样做的原因：交付验收完成后，任务主生命周期才闭环。

### 第五组：补齐异常和协商流程

1. 做变更请求。
2. 做取消请求。
3. 做主动流标。
4. 做延长招标截止。
5. 做无投标自动流标。

这样做的原因：这些都是主流程之外的分支，应该在主闭环稳定后补。

## 下一步建议

下一步建议先做“小范围重构发布任务到 `CreateTaskService`”，然后立刻做“任务详情页 + 投标功能”。

不要先做 TOP 甘特图、通知、复杂权限后台或角色管理页面。现在第一目标是把 TaskHub 的核心业务闭环做出来：

```text
发布任务
↓
投标
↓
选标
↓
交付
↓
验收完成
```
