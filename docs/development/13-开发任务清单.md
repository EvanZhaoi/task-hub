# 13 - TaskHub 开发任务清单

## 1. 文档作用

本章是 TaskHub 当前唯一的开发进度总表，用于记录：

1. 已经完成并通过验证的能力。
2. 第一期发布前必须完成的能力。
3. 时间允许时再加入第一期的能力。
4. 明确放到第二期、第三期或暂不开发的能力。

数据库结构仍以 `database/schema.sql` 为准，业务规则以 `docs/需求文档.md` 和 `docs/模块与数据库设计.md` 为准。

## 2. 状态定义

| 状态 | 含义 |
| --- | --- |
| 已完成 | 仓库已有可运行代码，并有测试或构建验证 |
| 部分完成 | 基础结构已经存在，但完整业务流程还未完成 |
| 第一期待办 | 第一次测试发布前必须完成 |
| 第一期候选 | 时间允许时加入第一期，不阻塞首次测试发布 |
| 第二期待办 | 第一版投标和选标稳定后继续开发 |
| 第三期待办 | 数据积累后开发的管理和效率能力 |
| 待外部确认 | 依赖总部接口、部署环境或产品规则 |
| 暂不做 | 当前已经明确不实现 |

## 3. 当前主流程

已经完成：

```text
SSO 授权码登录
    ↓
任务大厅与任务筛选
    ↓
发布招标任务
    ↓
任务详情、描述和附件
    ↓
单人 / 多人联合投标
    ↓
投标记录、成员和附件展示
    ↓
发布者选标
    ↓
生成并展示正式执行成员
```

第一期还需要补齐：

```text
直接指定成员发布任务
    ↓
任务大厅 / 我发布的 / 我的投标 / 我参与的
    ↓
权限与状态测试
    ↓
第一期测试发布
```

## 11. 第一期待办四：与我相关的任务

为了让用户快速找到自己的工作，第一期新增四个任务范围：

```text
任务大厅 | 我发布的 | 我的投标 | 我参与的
```

继续复用当前任务列表，不新建三套重复页面。

| 范围 | 查询规则 | 页面补充信息 |
| --- | --- | --- |
| 任务大厅 | 当前公开任务查询 | 保持当前列表行为 |
| 我发布的 | `task.created_by = 当前工号` | 显示状态和有效投标数量，便于进入选标 |
| 我的投标 | 当前工号在 `bid_member` 中角色为 OWNER | 显示本人最新投标状态、报价和版本 |
| 我参与的 | 当前工号是 Bid COLLABORATOR，或存在于 task_assignee | 显示“协作投标 / 负责人 / 执行协作者”等关系 |

具体子任务：

## 13. 第一期候选功能

以下功能有价值，但不阻塞“发布、投标、选标、直接指派、个人任务入口”的第一次测试发布：

| 任务 | 状态 | 说明 |
| --- | --- | --- |
| 撤回投标 | 第一期候选 | 截止前 OWNER 可撤回，写 BID_WITHDRAWN |
| 撤回后重投 | 第一期候选 | 新建 Bid，保留历史版本 |
| 无投标自动流标 | 第一期候选 | Scheduler 每分钟扫描，Service 必须幂等 |
| 发布者主动流标 | 第一期候选 | 有投标时可主动结束，必须填写原因 |
| 延长招标截止 | 第一期候选 | 只能 OPEN，日期必须为未来时间 |
| OPEN 任务取消 | 第一期候选 | 取消规则需要和主动流标区分清楚 |

若第一期时间不足，这些功能整体移动到第二期，不应压缩选标、直接指派和测试质量。

## 14. 第二期待办

| 模块 | 主要任务 |
| --- | --- |

## 16. 明确暂不做

- 微服务、DDD、CQRS、Event Sourcing。
- Repository / DAO。
- Kafka、Outbox、分布式事务。
- 本地 users 表。
- 通用逻辑删除框架。
- 执行过程中增删或更换成员。
- 复杂审批流、仲裁、工时统计。
- 图片富文本、协同编辑、任务聊天。
