# 21 - 任务紧急度字段

## 1. 本章目标

本章记录 TaskHub 为任务增加独立紧急度字段的实现结果。

此前任务大厅为了满足列表展示，临时使用 `complexity` 显示低、中、高紧急程度。这会混淆两个不同概念：

- 复杂度描述任务实现难度。
- 紧急度描述任务处理优先程度。

本次新增 `task.urgency`，发布者在发布任务时分别选择复杂度和紧急度。任务大厅和任务详情以后都读取真实紧急度，不再从复杂度推导。

## 2. 最终字段设计

`task` 表新增字段：

```sql
`urgency` VARCHAR(20) NOT NULL DEFAULT 'MEDIUM'
  COMMENT '紧急度：LOW/MEDIUM/HIGH'
```

允许值：

| 数据库存储值 | 页面文案 | 含义 |
| --- | --- | --- |
| `LOW` | 低 | 正常排期处理 |
| `MEDIUM` | 中 | 默认紧急程度 |
| `HIGH` | 高 | 需要优先关注 |

数据库增加 CHECK 约束：

```sql
CONSTRAINT `CHK_task_urgency`
  CHECK (`urgency` IN ('LOW', 'MEDIUM', 'HIGH'))
```

字段设置 `DEFAULT 'MEDIUM'` 有两个作用：

1. 执行已有数据库升级脚本时，历史任务会自动获得 `MEDIUM`。
2. 兼容尚未显式写入紧急度的内部脚本或测试数据。

正式发布任务接口仍要求前端明确提交 `urgency`，不能依赖数据库默认值替代用户选择。

## 3. 为什么紧急度不能继续复用复杂度

复杂任务不一定紧急，紧急任务也不一定复杂。例如：

| 任务 | 复杂度 | 紧急度 |
| --- | --- | --- |
| 修正一处生产环境错误文案 | LOW | HIGH |
| 重构历史报表模块 | HIGH | LOW |
| 一周内完成普通接口开发 | MEDIUM | MEDIUM |

如果两个概念共用一个字段，列表标签、筛选和后续排序都会表达错误。因此代码中也分别建立：

- `TaskComplexity`
- `TaskUrgency`

即使它们当前都使用 `LOW / MEDIUM / HIGH`，也不能合并成一个通用类型。

## 4. 数据库更新方式

### 4.1 全新数据库

全新环境继续以以下文件作为完整数据库结构标准：

```text
database/schema.sql
```

最新 `schema.sql` 已包含：

- `task.urgency`
- 默认值 `MEDIUM`
- 中文字段注释
- `CHK_task_urgency` 约束

### 4.2 已有数据库

已经初始化过 TaskHub 数据库的环境不能重新执行完整 `schema.sql`，因为完整脚本会删除并重建业务表。

已有环境只执行一次增量脚本：

```text
database/patches/20261014_add_task_urgency.sql
```

在项目根目录使用 MySQL CLI 的示例：

```bash
mysql -h 127.0.0.1 -P 3306 -u taskhub -p taskhub \
  < database/patches/20261014_add_task_urgency.sql
```

命令中的主机、端口、用户名和数据库名需要按当前环境修改。密码通过终端提示输入，不要写进命令或提交到 Git。

也可以在 VS Code 数据库插件中连接目标数据库，打开该 SQL 文件并执行。

该脚本不是通用 Migration，也不应重复执行。再次执行会因为字段或约束已经存在而失败。

### 4.3 执行后检查

```sql
SHOW COLUMNS FROM `task` LIKE 'urgency';

SELECT `id`, `title`, `complexity`, `urgency`
FROM `task`
ORDER BY `created_at` DESC
LIMIT 10;
```

历史任务的 `urgency` 应为 `MEDIUM`。

本次没有给 `urgency` 建普通索引。当前页面不按紧急度筛选或排序，为低基数字段提前建索引没有实际收益。未来真正增加紧急任务查询后，再根据查询条件评估组合索引。

## 5. 后端数据链路

发布任务时，紧急度经过以下链路：

```text
发布任务表单 urgency
    ↓
StoreTaskRequest 校验
    ↓
CreateTaskService
    ↓
task.urgency
    ↓
TASK_CREATED event_data.urgency
```

### 5.1 StoreTaskRequest

新增校验规则：

```php
'urgency' => [
    'required',
    'string',
    Rule::in(['LOW', 'MEDIUM', 'HIGH']),
],
```

对应中文提示包括：

- 未选择：`请选择任务紧急度。`
- 格式错误：`任务紧急度格式不正确。`
- 枚举错误：`任务紧急度只能选择低、中或高。`

前端选择器只能改善操作体验，后端校验才是可信的数据边界。

### 5.2 CreateTaskService

`CreateTaskService` 创建任务时写入：

```php
'urgency' => $validated['urgency'],
```

`TASK_CREATED` 的 `event_data` 同时保存创建时的紧急度快照：

```php
'urgency' => $task->urgency,
```

因此以后即使任务紧急度允许修改，仍然能够从事件中看到创建时的值。

### 5.3 Task Model

`Task::$fillable` 增加 `urgency`，允许 `CreateTaskService` 使用 Eloquent 批量赋值写入该字段。

`urgency` 是普通字符串枚举，不需要增加 Eloquent cast。

### 5.4 列表与详情 Props

`TaskController` 在任务大厅查询中显式选择 `urgency`，并在两种页面结构中返回：

- `taskItem()`：任务大厅列表项。
- `taskDetail()`：任务详情。

Controller 不把紧急度转换成中文。后端返回稳定的枚举值，React 根据枚举值决定页面文案和 Badge 样式。

## 6. 前端实现

### 6.1 发布任务

发布任务表单新增“紧急度”必填选择器：

- 低：`LOW`
- 中：`MEDIUM`
- 高：`HIGH`

默认值为 `MEDIUM`。

预算、复杂度和紧急度在桌面端位于同一行：

```text
┌──────────────────────┬───────────┬───────────┐
│ 预算金额（50%）      │ 复杂度    │ 紧急度    │
└──────────────────────┴───────────┴───────────┘
```

窄屏下自动改成纵向排列，各控件保持完整宽度。

### 6.2 任务大厅

任务卡片中的紧急程度徽标现在读取：

```tsx
task.urgency
```

不再读取：

```tsx
task.complexity
```

展示颜色：

| 紧急度 | Badge 视觉 |
| --- | --- |
| LOW | 低强度绿色 |
| MEDIUM | 提醒色 |
| HIGH | 危险色 |

### 6.3 任务详情

详情页标题区域现在同时展示：

- 任务状态。
- 复杂度。
- 紧急程度。
- 分配方式。

这样用户可以同时判断任务实现难度和处理优先级。

### 6.4 TypeScript 类型

新增独立类型：

```ts
export type TaskUrgency = 'LOW' | 'MEDIUM' | 'HIGH';
```

以下类型增加 `urgency: TaskUrgency`：

- `TaskListItem`
- `TaskDetail`
- 发布任务表单类型

这可以让 TypeScript 在编译阶段发现缺失字段或非法字符串。

## 8. 部署顺序

已有环境必须按以下顺序部署：

1. 备份数据库。
2. 执行 `database/patches/20261014_add_task_urgency.sql`。
3. 确认历史任务的紧急度为 `MEDIUM`。
4. 发布本次后端和前端代码。
5. 清理 Laravel 配置缓存并重新构建前端。
6. 发布一条测试任务，检查列表和详情紧急度。

必须先升级数据库，再发布读取 `task.urgency` 的应用代码。顺序反过来时，任务大厅会因为数据库缺少字段而查询失败。

自动化测试新增检查：

- 发布任务能够保存用户选择的 `HIGH` 紧急度。
- 任务大厅 Inertia Props 能返回任务紧急度。
- 任务详情 Inertia Props 能返回任务紧急度。
- SQLite 测试表包含 urgency，并用 MEDIUM 兼容历史测试数据。

## 10. 当前未增加的功能

本次只完成紧急度的创建、保存和展示，没有增加：

- 按紧急度筛选。
- 按紧急度排序。
- 自动根据截止时间修改紧急度。
- 紧急度修改审批。
- 紧急度专用数据库索引。

这些能力应在出现明确产品需求后再补充，避免把一个简单字段扩展成过度复杂的优先级系统。
